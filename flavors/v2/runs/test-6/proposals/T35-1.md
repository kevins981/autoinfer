# T35 proposal 1 (moonshot, leader-35): a streaming-bound decode step

## The idea
Make a decode step take the time its DRAM bytes take. Weight streaming would be **decoupled from the
activation dependency chain**: a run-ahead weight streamer keeps DRAM busy through every phase of the
step. Today DRAM goes quiet in those phases: all-reduce windows, norms/quant, GDN recurrence, attention,
kernel ramp-up and tail, the drafter. The GEMMs then consume weights that are already on chip (L2, 72 MB).
- Final form: a persistent decode-step kernel (or a few per layer group) with producer warps streaming
  weights in a fixed, precomputed order and consumer warps doing GEMM/norm/GDN/AR as activations
  arrive. The AR stays SM-driven through host-mapped memory, as the champion's hostar already is.
- Stage 2 option, same machinery: lossless entropy-coded FP8 weights. The measured byte entropy is
  6.55 bits/weight (CPU, layers 2/10/11/40/63), so up to 18% fewer weight bytes. Exact: the decoded
  bytes are the checkpoint's bytes.
- **Rejected assumption:** a decode step is a chain of dependent kernels, each streaming its own
  weights only once its input is ready. The champion bolts a partial L2 prefetch onto each AR (its own
  comment says ~40% of the hinted range lands). That is a patch on this assumption, not a removal.

## Measured (my jobs)
- Job 352 (nsys, champion T31-003, 64 prompts): a full decode step (M=48) has 23.3 ms GPU busy:
  hostar AR+prefetch 6.0, Marlin gate_up 6.0, t31b GEMMs 6.6, GDN replay 1.7, lm_head 1.0, rest ~2.
- **Step time is mostly fixed cost:** M=3 (1 sequence) 19.0 ms, M=24 20.2, M=48 23.3 (job 352).
- One GDN layer in steady decode runs ~345 us of kernels for ~191 MB of FP8 weights (+GDN state).
  At ~0.95 TB/s the weights alone need ~200 us, so the layer runs at ~55% of DRAM bandwidth.
  Examples: gate_up Marlin takes 94 us for 89 MB right after an AR that was meant to prefetch it, so
  that prefetch is not effective. The AR after gdn_out takes 50 us.
- Job 353 (same job, 200 prompts): budget 2048 → 1069.0 tok/s; 192 → 1041.1; 128 → 870.5. Prefill adds
  ~16% to wall time (from step counters); decode steps are ~84%.
- Job 355 (cross-job vs 353): MTP k=3 → 1041.3 tok/s (−2.6%), acceptance 2.33 → 2.69. Wider verification
  costs more than it gains here, so I'm not proposing tree speculation.

## Upside (argued from limits)
Per-GPU decode-step DRAM floor: weights 12.15 GB at ~0.95 TB/s = 12.8 ms, GDN state ~1.5 ms, lm_head and
drafter weights ~1.5 ms, so ≈ 15.8 ms. The champion takes 23.3 ms. If fully realised: decode steps −32%,
and with decode at ~84% of wall time that is **≈ +35% over the champion**. With lossless weight
compression on top, the floor drops ~2 ms more (≈ +45%).
(Floor numbers: weight bytes and bandwidth are *assumed* from the spec and the config; the step times are
*measured* in job 352.)

## Riskiest assumption and the cheapest test
**Assumption:** the idle-DRAM windows add up to ≥5 ms per step, and a run-ahead streamer can fill them by
holding ~40-50 MB of upcoming weights in L2 without thrashing, so the consuming GEMMs then run near L2 speed.
The champion's own experience is a warning: hint prefetches land only partly, and real-load prefetch
needs many SMs.
**Test (milestone 1, ~15 GPU-min):**
(a) ncu DRAM-throughput accounting over one decode layer of the champion (per kernel: DRAM bytes and
    duration), to find exactly where and for how long DRAM idles.
(b) A standalone microbenchmark on one GPU with the champion's real kernels (t31b, Marlin) and random
    weights of the real shapes. It replays one GDN layer's chain with the AR replaced by a calibrated
    stall, two ways: serial, and with a concurrent run-ahead streamer (real loads into L2 with
    evict_last, bounded lookahead, few SMs). Measure layer time against bytes/BW.
**Kill criterion:** if (b) can't get one layer below ~290 us (from ~345 us), the core idea is wrong on this
hardware. That threshold is ≥5% at whole-run level after Amdahl. I'd then stop and write it up.

## Roadmap
1. (15 GPU-min) Milestone 1 above. It must show the layer-time reduction in the microbenchmark.
2. (40 GPU-min) Streamer in the real server, still using the champion's kernels: a side-stream/graph
   branch runs ahead across layer boundaries, replacing the per-AR hint prefetch. Unofficial A/B vs the
   champion must show ≥ +5%.
3. (60 GPU-min) Persistent fused per-layer decode kernel (GEMMs + norm/quant + AR in one launch with
   producer/consumer warps), removing ramp/tail and launch boundaries. A/B must move toward the
   ≥ +15% target.
4. (40 GPU-min) Optional lossless weight codec inside the streamer. Then official eval, plus 128K and
   GSM8K checks. The math is unchanged (same GEMM kernels and accumulation order where possible; any
   change gets numeric checks).
