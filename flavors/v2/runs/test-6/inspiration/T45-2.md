# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Per-item overhead

**The principle.** The cost of a piece of work often has two parts: one that grows with its size, and a fixed part paid every time regardless of size (setting up, starting, switching, handing over). When items are small, the fixed part dominates. The fixed part belongs to the act of starting, not to the work itself, so several items can share one.

**The waste.** Fixed costs paid more often than necessary.

**General directions.**
- **Group items:** pay the fixed part once for many.
- **Join steps:** let an item pass through several steps without stopping and restarting between them.
- **Stay set up:** keep the preparation between items instead of tearing it down and rebuilding it.
- **Shrink the fixed part:** if it can't be shared, make it cheaper.

**Illustrations** (examples only; the best use of this principle may look like none of them). A bus carries fifty people with one driver. Laundry is done by the load. Goods cross the ocean in containers, not parcel by parcel.

(card: `10-per-item-overhead.md`)

### Repetition

**The principle.** Any piece of work is a function: it takes inputs and produces an output. The output contains nothing that wasn't already determined by the inputs. So work is only necessary when the inputs are new. If the inputs were seen before, the output already exists somewhere. If part of the inputs is new, only the part of the output that depends on it needs to be made.

This holds for computing a value, and equally for moving or storing one: sending something to a place that already has it is the same waste.

**The waste.** The work done, minus the work the new information required.

**General directions.**
- **Remember:** keep an output so the work isn't done again. This trades memory for work.
- **Share:** produce an output once and let everyone who needs it use the same copy.
- **Update by difference:** when the inputs change a little, compute only what the change affects.
- **Do it ahead:** if the inputs are known long before the output is needed, the work can be done once, early.

**Illustrations** (examples only; the best use of this principle may look like none of them). Incremental compilation rebuilds only what a change touched. Rsync sends only the parts of a file the other side lacks. A spreadsheet recomputes only the cells that depend on the edited one.

(card: `01-repetition.md`)

### Predictability

**The principle.** Waiting for a result is necessary only if the result can't be predicted. If a guess is usually right, and checking a guess costs less than waiting for the answer, work can go ahead on the guess and be corrected in the rare cases it was wrong. The gain is roughly (chance of being right x time saved) - (chance of being wrong x work wasted). It needs three things: a cheap guess, a cheap check, and a way to undo.

**The waste.** Time spent waiting for an answer that was largely known in advance.

**General directions.**
- **Guess and verify:** proceed on the likely answer; check it when the real one arrives.
- **Prepare ahead:** get ready what is likely to be needed next.
- **Follow several possibilities:** and keep the one that turns out right.
- **Improve the odds or lower the price:** a better guess, a cheaper check, or a cheaper undo.

**Illustrations** (examples only; the best use of this principle may look like none of them). A processor guesses which way a branch will go and runs ahead. A waiter starts a regular's usual order when they walk in. A disk reads the next blocks before they are asked for.

(card: `08-predictability.md`)

### Trade-offs

**The principle.** Improving one thing often worsens another. The usual response is to pick a point between the two. But the two needs seldom apply at the same time, in the same place, to the same things. If they can be separated, each can be met in full.

(This card is not a kind of waste. It is a way out when two goals seem to conflict.)

**The waste.** Settling for a compromise when the two needs could have been separated.

**General directions.**
- **Separate by time:** one way now, the other way later.
- **Separate by place:** one part built one way, another part the other way.
- **Separate by condition:** one way for some cases, the other way for the rest.
- **Separate by scale:** the whole behaves one way, its parts another.

**Illustrations** (examples only; the best use of this principle may look like none of them). Bifocal glasses give near and far vision in different parts of the lens. A road reverses a lane for the morning and the evening rush. An aircraft wing changes shape between landing and cruising.

(card: `21-trade-offs.md`)

### Idleness

**The principle.** A system is a set of resources, each able to do work at some rate. A job is a set of pieces of work, where some pieces need the results of others. Two things set the minimum time for the job:
- **The longest chain of true dependencies:** pieces that really need each other's results must run one after another.
- **Total work divided by total capacity:** every resource working all the time can't go faster than this.

Any time beyond those two limits is waiting that nothing requires. It usually comes from the order in which the work was arranged, not from what the work needs.

**The waste.** A resource has free capacity, and a piece of work has all its inputs ready, but the work isn't running there.

**General directions.**
- **Separate true dependencies from arranged order:** find which waits are needed and which are only habit.
- **Run ready work on free capacity:** at the same time as other work, or overlapping with it.
- **Shorten the longest chain:** restructure the work so pieces depend on less, or on results that arrive earlier.
- **Move work toward free capacity:** a piece can run on a different resource, even one that does it more slowly, if that resource would otherwise wait.

**Illustrations** (examples only; the best use of this principle may look like none of them). A processor starts the next instruction before the current one finishes. A kitchen prepares side dishes while the main dish is in the oven. A program continues with other work while waiting for a disk read.

(card: `06-idleness.md`)

## This machine: hardware

### Dividing one GPU into parts

**What it is.** Green contexts give a program several lightweight contexts on one GPU, each owning a fixed subset of the SMs. On this chip family a part is at least 4 SMs, in multiples of 2. Work in one part does not take SMs from another. The documentation notes that disjoint parts are not guaranteed to run at the same time.

**What it makes possible.** Different kinds of work can each get a known share of the chip instead of contending for all of it.

**How this was checked.** From the documentation; not tried on this machine.

**Where to read more.** CUDA Programming Guide: Green Contexts.

(card: `13-dividing-one-gpu-into-parts.md`)

### Main memory and how fast it can be read

**What it is.** Each GPU has 24 GB of GDDR6X memory on a 384-bit bus clocked at 10,501 MHz. At 21 Gbit/s per pin that is a theoretical peak of 1,008 GB/s. There is no error correction. The memory is not shared between the two GPUs.

**What it makes possible.** The peak rate puts a floor under any step that must read a given number of bytes: bytes divided by rate. Comparing that floor with a step's measured time shows whether the step is limited by reading memory or by something else.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes). The peak rate is arithmetic from the bus width and data rate, not a measurement.

**Where to read more.** Ada Tuning Guide; the Nsight Compute memory metrics.

(card: `05-main-memory-and-how-fast-it-can-be-read.md`)

### A very large second-level cache

**What it is.** All 128 SMs of a GPU share one second-level cache of 72 MiB. That is large next to many of the arrays a program reads repeatedly.

**What it makes possible.** Data that fits in the cache and is read again soon does not have to come from main memory again. Whether it is still there depends on what else passed through the cache in between, which the order of work decides.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** Ada Tuning Guide; CUDA Programming Guide: L2 Cache Control.

(card: `06-a-very-large-second-level-cache.md`)

### Single instructions that do a loop's work

**What it is.** The instruction set has single instructions for jobs that are usually written as loops or several steps: count the set bits in a word, find the highest set bit, reverse bits, extract or insert a bit field; any three-input boolean function; a four-way 8-bit dot product into a 32-bit sum; reduce a value across all 32 threads of a warp (sum, min, max, and, or, xor); find which threads of a warp hold the same value; packed pairs of 16-bit floats in one register, with a fused multiply-add that can clamp at zero; an approximate tanh.

**What it makes possible.** Work on bits, small integers and whole warps can cost one instruction where a straightforward version costs many, and can stay in registers without touching memory.

**How this was checked.** Each instruction was assembled for this chip (`ptxas -arch=sm_89`); not run.

**Where to read more.** PTX ISA reference: integer, logic and warp-level instructions; CUDA Programming Guide: Device-Callable APIs and Intrinsics.

(card: `04-single-instructions-that-do-a-loop-s-work.md`)

### Four one-way lanes

**What it is.** Each PCIe link carries data in both directions at once at full rate, and each GPU has its own link and two copy engines. So there are four independent one-way paths: host to GPU and GPU to host, for each of the two GPUs.

**What it makes possible.** An exchange between the GPUs does not have to be a sequence of turns. Both GPUs can send and receive at the same moment.

**How this was checked.** Follows from the link type and the device's reported copy engines; simultaneous transfers were not measured here.

**Where to read more.** PCI Express specification summaries; CUDA Programming Guide: Asynchronous Execution.

(card: `22-four-one-way-lanes.md`)

## This machine: software

### Compiling a whole sequence of operations as one

**What it is.** The framework can trace a model's sequence of operations and hand it to a compiler as one unit, which may fuse operations, drop intermediate results and generate code specialized to the shapes seen. Separately, a sequence of GPU operations can be captured once and replayed as a graph.

**What it makes possible.** Boundaries between operations are a choice of the code as written, not of the computation.

**How this was checked.** Part of the installed framework (torch 2.14); not exercised here.

**Where to read more.** PyTorch documentation: `torch.compile`, `torch.fx`, CUDA graphs.

(card: `04-compiling-a-whole-sequence-of-operations-as-one.md`)

### The operating system: what a user can control

**What it is.** Without administrator rights a user can still: choose which cores a thread or process may run on; choose that a thread's memory is allocated on the half of the host where it first touches it; request large pages for a memory range (the system grants them on request, not by default); lock up to about 15.7 GB of memory so it is never paged out; lower a process's priority; create shared memory. A tool to set core affinity is installed; the usual tool for memory placement is not, though the underlying system calls are available.

**What it makes possible.** Where threads run and where memory sits is left to the system's defaults unless the program says otherwise.

**How this was checked.** Read from `ulimit`, `/sys/kernel/mm/transparent_hugepage/` and the installed tools.

**Where to read more.** `man` pages: `sched_setaffinity`, `mbind`, `madvise`, `mlock`, `taskset`.

(card: `11-the-operating-system-what-a-user-can-control.md`)

### The communication library, beyond one operation

**What it is.** The library that moves data between GPUs (NCCL 2.30) offers more than the sum-across-GPUs operation: broadcast, reduce to one GPU, gather from all, reduce-then-scatter, and plain send and receive between two GPUs. Several operations can be grouped and issued together. Buffers can be registered ahead of time. It has a Python interface. Its newest feature, communication started from inside a kernel, needs direct GPU-to-GPU access and so does not apply on this machine.

**What it makes possible.** The exchange pattern between the GPUs is a choice from a larger set than the one in use, and the library is not the only way to move data.

**How this was checked.** The package and its Python interface are installed. Which transport it selects on this machine was not checked here.

**Where to read more.** NCCL user guide and release notes.

(card: `07-the-communication-library-beyond-one-operation.md`)

### Parallel building blocks

**What it is.** A library of general parallel algorithms for the GPU is installed, in C++ and with a Python interface: sort, scan (running totals), reduce, select the items that meet a condition, partition, remove duplicates, histogram, run-length encode, search, merge.

**What it makes possible.** Problems that look inherently sequential, such as compacting a list or grouping equal items, have well-known parallel forms that are already written.

**How this was checked.** The package is installed (CCCL 13.3); not exercised here.

**Where to read more.** CCCL documentation (Thrust, CUB, `cuda.cccl`).

(card: `06-parallel-building-blocks.md`)

### The framework underneath

**What it is.** The framework keeps its own pool of GPU memory and hands out pieces without asking the driver each time; the pool's behaviour can be tuned and inspected. New operations can be written in C++ or CUDA and loaded as extensions, built ahead of time or when the program starts. The framework exposes streams, events, pinned host memory and non-blocking copies. Each operation passes through a dispatch layer on the host before any GPU work is issued.

**What it makes possible.** The framework's defaults are one arrangement among several it supports, and anything it lacks can be added beside it.

**How this was checked.** From the installed framework (torch 2.14); not exercised here.

**Where to read more.** PyTorch documentation: CUDA semantics, memory management, C++ extensions.

(card: `10-the-framework-underneath.md`)
