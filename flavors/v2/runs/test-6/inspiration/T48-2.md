# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Trade-offs

**The principle.** Improving one thing often worsens another. The usual response is to pick a point between the two. But the two needs seldom apply at the same time, in the same place, to the same things. If they can be separated, each can be met in full.

(This card is not a kind of waste. It is a way out when two goals seem to conflict.)

**The waste.** Settling for a compromise when the two needs could have been separated.

**General directions.**
- **Separate by time:** one way now, the other way later.
- **Separate by place:** one part built one way, another part the other way.
- **Separate by condition:** one way for some cases, the other way for the rest.
- **Separate by scale:** the whole behaves one way, its parts another.

**Illustrations** (examples only; the best use of this principle may look like none of them). Bifocal glasses give near and far vision in different parts of the lens. A road reverses a lane for the morning and the evening rush. An aircraft wing changes shape between landing and cruising.

(card: `21-trade-offs.md`)

### Imbalance

**The principle.** A system has several resources: time, memory, capacity to move things, different kinds of processing. They are rarely all scarce at once. Usually one limits the system and the others have room to spare. Most work can be done in more than one way, each using a different mix of resources. Gains come only at the limiting resource; spending the others costs nothing until they run out.

**The waste.** A plentiful resource left unused while a scarce one limits the system.

**General directions.**
- **Find the limit:** which resource is the system actually waiting for?
- **Spend the plentiful to save the scarce:** choose the way of working that leans on what is spare.
- **Trade in either direction:** more memory for less work, or more work for less memory or movement.
- **Check again:** after a change the limit may have moved to another resource.

**Illustrations** (examples only; the best use of this principle may look like none of them). A table of answers spends space to save time; compression spends time to save space. A slow cooker spends hours to save attention. A factory with idle machines and too few workers reorganizes around the workers.

(card: `14-imbalance.md`)

### Unused results

**The principle.** Work has value only through what uses its output. Follow any output forward: if nothing reads it, or only part of it is read, the unread part bought nothing. This happens because the producer usually doesn't know what the consumer will need, so it produces everything to be safe.

**The waste.** Work whose output nobody uses, and the unused part of outputs that are only partly used.

**General directions.**
- **Produce on demand:** wait until something asks for the output.
- **Produce only the part asked for:** let the request say how much is needed.
- **Tell the producer:** pass the consumer's needs back to where the work is done.
- **Stop early:** once the answer is determined, the rest of the work adds nothing.

**Illustrations** (examples only; the best use of this principle may look like none of them). A restaurant cooks to order instead of cooking the whole menu. A search stops at the first match when one is enough. A map loads only the area on the screen.

(card: `02-unused-results.md`)

### Repetition

**The principle.** Any piece of work is a function: it takes inputs and produces an output. The output contains nothing that wasn't already determined by the inputs. So work is only necessary when the inputs are new. If the inputs were seen before, the output already exists somewhere. If part of the inputs is new, only the part of the output that depends on it needs to be made.

This holds for computing a value, and equally for moving or storing one: sending something to a place that already has it is the same waste.

**The waste.** The work done, minus the work the new information required.

**General directions.**
- **Remember:** keep an output so the work isn't done again. This trades memory for work.
- **Share:** produce an output once and let everyone who needs it use the same copy.
- **Update by difference:** when the inputs change a little, compute only what the change affects.
- **Do it ahead:** if the inputs are known long before the output is needed, the work can be done once, early.

**Illustrations** (examples only; the best use of this principle may look like none of them). Incremental compilation rebuilds only what a change touched. Rsync sends only the parts of a file the other side lacks. A spreadsheet recomputes only the cells that depend on the edited one.

(card: `01-repetition.md`)

### Predictability

**The principle.** Waiting for a result is necessary only if the result can't be predicted. If a guess is usually right, and checking a guess costs less than waiting for the answer, work can go ahead on the guess and be corrected in the rare cases it was wrong. The gain is roughly (chance of being right x time saved) - (chance of being wrong x work wasted). It needs three things: a cheap guess, a cheap check, and a way to undo.

**The waste.** Time spent waiting for an answer that was largely known in advance.

**General directions.**
- **Guess and verify:** proceed on the likely answer; check it when the real one arrives.
- **Prepare ahead:** get ready what is likely to be needed next.
- **Follow several possibilities:** and keep the one that turns out right.
- **Improve the odds or lower the price:** a better guess, a cheaper check, or a cheaper undo.

**Illustrations** (examples only; the best use of this principle may look like none of them). A processor guesses which way a branch will go and runs ahead. A waiter starts a regular's usual order when they walk in. A disk reads the next blocks before they are asked for.

(card: `08-predictability.md`)

## This machine: hardware

### Every transfer has a fixed cost

**What it is.** Moving data across a link costs a fixed amount of time that does not depend on the size: a call into the driver, setting up the transfer, and learning that it has finished. Only above some size does the time grow with the number of bytes.

**What it makes possible.** For small transfers the count matters more than the bytes. The size at which the fixed part stops dominating can be measured, and it tells you which regime a given exchange is in.

**How this was checked.** A general property of this kind of link; the fixed cost on this machine is not stated here. Measure it.

**Where to read more.** CUDA Programming Guide: Asynchronous Execution.

(card: `23-every-transfer-has-a-fixed-cost.md`)

### Memory and signals shared between processes

**What it is.** GPU memory allocated in one process can be opened in another, which then reads and writes the same bytes without a copy. Events can be shared the same way, so one process can wait for work another process started. Memory pools give allocation and release that are ordered with the work on a stream, and a pool can be created so that its memory is exportable.

**What it makes possible.** Work on one GPU can be split across processes without paying for copies between them.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Interprocess Communication; Stream-Ordered Memory Allocator.

(card: `11-memory-and-signals-shared-between-processes.md`)

### The paths between the parts

**What it is.** Each GPU connects to the host by its own PCIe link (generation 4, 16 lanes) on its own port. Both links attach to the first processor socket. A link carries about 32 GB/s in each direction at most. A GPU reads its own memory about 30 times faster than that.

**What it makes possible.** Anything that crosses a link is far more expensive per byte than anything that stays on a GPU. How many bytes cross, and how often, is set by how the work is divided.

**How this was checked.** Topology read from `nvidia-smi` and `lspci`. The link rate is the standard's figure, not a measurement.

**Where to read more.** PCI Express specification summaries; `nvidia-smi topo -m`.

(card: `20-the-paths-between-the-parts.md`)

### Work described ahead of time as a graph

**What it is.** A sequence of kernels and copies, with their dependencies, can be recorded once as a graph and then launched as a unit, any number of times. Parameters of individual nodes can be updated without rebuilding the graph. Graphs can contain conditional nodes (if, while, switch) whose condition is written by a kernel on the GPU, so a decision does not have to go back to the host. A kernel can itself launch a graph.

**What it makes possible.** The cost of issuing many small pieces of work is paid once, and some control flow can stay on the GPU.

**How this was checked.** From the documentation; conditional nodes and device-side launch were not tried on this machine.

**Where to read more.** CUDA Programming Guide: CUDA Graphs.

(card: `15-work-described-ahead-of-time-as-a-graph.md`)

### Matrix hardware: the data types it accepts

**What it is.** The matrix-multiply units (tensor cores) work on small fixed tiles, one warp at a time. On this chip they accept: 16-bit float, bfloat16, a 19-bit float (TF32), 64-bit float, 8-bit and 4-bit integers, single bits (with XOR or AND followed by a bit count), and two 8-bit float formats (E4M3 and E5M2, which can be mixed in one product). The 8-bit floats accumulate in 32-bit float. Tile depth grows as the type shrinks: 16 for the 16-bit floats, 32 for 8-bit types, 64 for 4-bit, 256 for single bits. There is a sparse form in which one operand has half its values removed in a fixed pattern. Single instructions convert pairs of 32-bit floats to and from the 8-bit float formats.

**What it makes possible.** The same matrix hardware does several times more multiplies per instruction on narrower types, and narrower operands are also fewer bytes to fetch.

**How this was checked.** Each instruction was assembled for this chip (`ptxas -arch=sm_89`); not run.

**Where to read more.** PTX ISA reference: warp-level matrix instructions (`mma`, `mma.sp`), `cvt`.

(card: `02-matrix-hardware-the-data-types-it-accepts.md`)

## This machine: software

### Down to the instructions

**What it is.** The compiler's intermediate language (PTX) can be read, written by hand, and placed inline inside C++ code. The assembler reports registers used and spilled per kernel. The final machine instructions can be disassembled from any compiled kernel, including ones from libraries. The profiler can attribute time to single source lines and instructions.

**What it makes possible.** What a kernel really does is visible, and what the higher-level languages do not expose can still be written.

**How this was checked.** The tools are installed (`ptxas`, `nvdisasm`, `cuobjdump`) and the assembler was used to check the hardware cards.

**Where to read more.** PTX ISA reference; CUDA binary utilities documentation.

(card: `03-down-to-the-instructions.md`)

### Ready-made math libraries

**What it is.** NVIDIA's tuned libraries are installed: dense linear algebra (including a lightweight matrix-multiply interface with many formats, and batched forms), sparse linear algebra, matrix multiply with one operand pruned in the fixed pattern the matrix hardware supports, solvers, Fourier transforms, random numbers, the standard deep-learning operations, image and JPEG routines, and reading files directly into GPU memory.

**What it makes possible.** Some of these implement an operation in a way nobody would write by hand, and some expose hardware modes that are otherwise awkward to reach.

**How this was checked.** The packages are installed; which code paths each takes on this chip was not checked.

**Where to read more.** cuBLAS, cuSPARSE, cuSPARSELt, cuSOLVER, cuFFT, cuRAND, cuDNN, NPP, nvJPEG and cuFile documentation.

(card: `05-ready-made-math-libraries.md`)

### The communication library, beyond one operation

**What it is.** The library that moves data between GPUs (NCCL 2.30) offers more than the sum-across-GPUs operation: broadcast, reduce to one GPU, gather from all, reduce-then-scatter, and plain send and receive between two GPUs. Several operations can be grouped and issued together. Buffers can be registered ahead of time. It has a Python interface. Its newest feature, communication started from inside a kernel, needs direct GPU-to-GPU access and so does not apply on this machine.

**What it makes possible.** The exchange pattern between the GPUs is a choice from a larger set than the one in use, and the library is not the only way to move data.

**How this was checked.** The package and its Python interface are installed. Which transport it selects on this machine was not checked here.

**Where to read more.** NCCL user guide and release notes.

(card: `07-the-communication-library-beyond-one-operation.md`)

### Ways to observe

**What it is.** Tools that work here without administrator rights: a per-kernel profiler with hardware counters, down to source lines and instructions (Nsight Compute); a timeline tracer for host and GPU activity (Nsight Systems); the framework's own profiler; a GPU debugger; sampling of GPU state (utilization, clocks, power, link speed, memory) through `nvidia-smi` or its library; and the Linux `perf` tool for a user's own processes. On this machine GPU hardware counters may be usable on the first GPU only.

**What it makes possible.** Anything that can be observed can be checked instead of assumed, including what the hardware does underneath the software.

**How this was checked.** The tools are installed and have been used on this machine.

**Where to read more.** Nsight Compute and Nsight Systems documentation; `man perf`; NVML reference.

(card: `13-ways-to-observe.md`)

### Sharing without copying

**What it is.** Several mechanisms let two parties use the same bytes. Host processes can share memory by name (63 GB available in the memory-backed file system). GPU memory can be shared between processes. Libraries in one process can hand each other GPU arrays without a copy through a standard exchange format (DLPack) or a common array interface. Message passing between processes is available with zero-copy for large messages.

**What it makes possible.** A boundary between processes or between libraries does not have to cost a copy.

**How this was checked.** The mechanisms are present in the installed software; not exercised here.

**Where to read more.** DLPack; PyTorch `torch.multiprocessing`; CUDA Programming Guide: Interprocess Communication; ZeroMQ guide.

(card: `08-sharing-without-copying.md`)
