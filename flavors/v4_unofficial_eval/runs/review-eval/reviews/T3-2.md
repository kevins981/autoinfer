**I would file this as a valid T3 change for the configured serving path, with performance still provisional.** I found no model-state race, unmatched stream fork, or target leak on normal execution. There are three robustness issues worth recording or fixing.

I verified that T3 changes only the three named files relative to T2-007, and that the filed `change.diff` exactly matches the current workspace.

1. **The fork/join is safe on the configured graph paths.** In [l2_prefetch.py:74](workspaces/t3-pf/vllm/vllm/distributed/device_communicators/l2_prefetch.py:74), the side stream waits for the current stream before reading. In [host_mapped_all_reduce.py:208](workspaces/t3-pf/vllm/vllm/distributed/device_communicators/host_mapped_all_reduce.py:208), HMAR runs on the current stream, which then waits for prefetch completion. Both operations finish before the following norm/GEMM proceeds.

   FULL capture records those dependencies and weight addresses; replay does not need Python `set_target`/`take` to execute again. For breakable PIECEWISE capture, the fork has already joined before an attention boundary ends the segment. The GDN breakpoints are inside the attention core, after the input norm and projections ([qwen_gdn_linear_attn.py:2511](workspaces/t3-pf/vllm/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:2511)). Eager execution follows the same dependencies.

   This conclusion covers the actual configuration: compilation is `NONE`, breakable graphs enabled, and one graph warmup. It does **not** establish compatibility with torch.compile-based piecewise execution. Lazy stream/dummy creation and Triton compilation are exercised before capture in the supplied microbench; the server logs also show successful graph capture. I see no initialization blocker for this run, but initialization before capture would make that contract clearer.

2. **Normal fallback does not leak the target into another collective.** The model brackets each individual norm with `set_target` and `clear` ([model.py:457](workspaces/t3-pf/vllm/vllm/models/qwen3_5/nvidia/model.py:457), [model.py:487](workspaces/t3-pf/vllm/vllm/models/qwen3_5/nvidia/model.py:487)). The dynamic-128 norm executes one explicit TP all-reduce. HMAR consumes the target once; if HMAR is disabled or ineligible, dispatch uses another backend without consuming it, and the following `clear()` removes it ([cuda_communicator.py:430](workspaces/t3-pf/vllm/vllm/distributed/device_communicators/cuda_communicator.py:430)). NCCL itself never launches this prefetch.

   Large mixed steps therefore incur target preparation but no prefetch. The first target layer has no residual and sets no input-projection target. MTP likewise begins with `residual=None` ([mtp.py:145](workspaces/t3-pf/vllm/vllm/models/qwen3_5/nvidia/mtp.py:145)): its input projection is skipped, its post-attention norm can prefetch gate-up, and its final all-reduce sees no pending target.

   **Cleanup gap:** neither bracket uses `try/finally`. An exception before `clear()` can leave `_pending` populated. Normal subsequent decoder entry overwrites it, but exception recovery followed by another HMAR call could consume the stale target. Use scoped cleanup if recovery is intended.

3. **The device dictionary is correct only with a matching current device.** [l2_prefetch.py:69](workspaces/t3-pf/vllm/vllm/distributed/device_communicators/l2_prefetch.py:69) selects streams and dummy storage using `current_device()`, while `all_reduce` also obtains the current device’s stream without guarding `inp.device`. There is no check that the target, input, and selected stream share a device. The C++ HMAR guard happens later, inside the extension.

   Serial execution with the current device correctly selected works, including switching devices between calls. Calling with another device current can fail during prefetch. Also, `_pending` is process-global, so the dictionary does not make concurrent model threads safe. These do not affect the present one-GPU-per-rank path. For broader support, guard the entire operation with `inp.device`, verify the target’s device, and make pending state scoped/thread-local.

4. **“Reads only” needs a small qualification: the dummy can be written, and its store can race.** At [l2_prefetch.py:34](workspaces/t3-pf/vllm/vllm/distributed/device_communicators/l2_prefetch.py:34), every program conditionally stores to the same scalar. The sentinel is not an impossible sum: these are integer sums of raw weight bits. Two programs reaching it would write the same address without synchronization.

   The dummy is private, retained globally, and never read by model computation, so I do not see an output-correctness consequence. Nevertheless, this is a real conditional write/write race. A retained dummy array with one unconditional store per program would preserve the load dependency and remove the race. The weight flattening itself creates a view, not a weight copy; the masked reads stay within the admitted contiguous or transposed-contiguous weight storage.

5. **The performance evidence supports overlap, but does not isolate the cache mechanism completely.** Job 47 measures savings of **9.94 µs for gate-up** and **9.40 µs for qkvz** at 16 MiB. The matrices rotate through working sets larger than L2, which is a useful cold-weight approximation. Moving 16 MiB of weight traffic into an approximately 43–47 µs communication window plausibly explains these savings.

   Limits of [hmar_pf_bench.py:23](agents/leader-3.w1/hmar_pf_bench.py:23):

   - GEMM uses an independent activation; the intervening norm/quantization and production BA overlap are absent.
   - Only M=48, gate-up, and GDN qkvz are covered. Full-attention qkv and the smaller MTP batches are not.
   - The “AR only, prefetch 24MB” timing includes prefetch completion and the join. Its increase does **not** prove the HMAR kernel itself slowed.
   - There are no counters or kernel timelines separating L2 warming from changed scheduling/resource contention.

   Thus I would write “consistent with hiding weight fetches during HMAR,” rather than claim the entire gain has been causally attributed to L2 hits.

   Job 48’s **+4.99%** is encouraging, with similar acceptance lengths, but remains a one-start-per-mode screen. The official harness was still incomplete when I inspected it.

6. **The most useful next tuning is per target and per communication window.** The implementation’s “16 MB” means **16 MiB**. That covers approximately 19% of gate-up, 40% of qkvz, and 46% of full-attention qkv. A common byte limit need not be optimal across them.

   I would prioritize separate limits for gate-up/qkvz/qkv and smaller HMAR messages, especially MTP. Compare the contiguous prefix with ranges matching early GEMM tile consumption. Larger sizes already regress in the microbench, so increasing coverage alone is not promising.

   L2 eviction of KV or GDN state cannot change their values, but can erase the performance benefit. The microbench has neither workload. Production timelines and cache/DRAM traffic would establish whether prefetch displaces useful state; short- and long-context performance would show the practical consequence. Weight scales and BA weights are possible additional targets, but their small size makes them secondary candidates.
