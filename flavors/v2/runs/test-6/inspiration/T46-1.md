# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Representation

**The principle.** The same information can be written in many forms. Forms differ in size, and in which operations are cheap on them. The cost of storing, moving and processing follows the form, not the information. A form is usually chosen once, for convenience, and everything afterwards pays for it.

**The waste.** Extra size and extra steps caused by the form, not by the information.

**General directions.**
- **A smaller form:** no larger than the information it holds.
- **A form that makes the frequent operation cheap:** even if rare operations get dearer.
- **Arrange for use:** put next to each other what is used together.
- **Convert once:** at the edge, not repeatedly inside.
- **Several forms:** the same information kept in different forms for different uses.

**Illustrations** (examples only; the best use of this principle may look like none of them). Arithmetic is easy in Arabic numerals and hard in Roman ones. A phone book is sorted by name because that is how it is searched. A map and a list of turns hold the same route for different uses.

(card: `13-representation.md`)

### Distance

**The principle.** Work needs its inputs at the place where it happens. Moving things takes time in proportion to how much is moved and how far, and the paths have limited capacity. Time spent moving is not time spent working. How much movement there is depends on where things are kept and where the work is done, and both are choices.

**The waste.** Movement that a different placement would avoid.

**General directions.**
- **Bring the work to the data:** instead of the data to the work.
- **Keep together what is used together:** so one trip serves many needs.
- **Move less:** only the part that is needed, or a smaller form of it.
- **Move once:** not the same thing back and forth.
- **Keep the most used nearest:** the nearest places are few; give them to what is needed most often.

**Illustrations** (examples only; the best use of this principle may look like none of them). A workshop keeps its most used tools within arm's reach. A retailer puts warehouses near its customers. A question is sent to the database instead of fetching the whole table to answer it.

(card: `09-distance.md`)

### Overqualified work

**The principle.** Expensive work is often applied to many candidates, of which only a few matter to the final answer. If a cheap test can tell which candidates cannot matter, the expensive work is needed only for the rest. The final answer still comes from the expensive, exact work, so it stays exact. The cheap test only has to avoid ruling out a candidate that matters.

**The waste.** Exact work spent on candidates that a cheaper test would have eliminated.

**General directions.**
- **Cheap pass first:** then exact work on the survivors only.
- **Use bounds:** a cheap bound can prove a candidate cannot win without evaluating it.
- **Stages of rising cost:** each stage removes candidates before the next, dearer one.
- **Order the tests:** cheapest and most selective first.

**Illustrations** (examples only; the best use of this principle may look like none of them). Security screens everyone quickly and searches a few by hand. An index rules out most rows before any is read. A chess program drops moves that a bound shows cannot beat the best found so far.

(card: `05-overqualified-work.md`)

### Unused results

**The principle.** Work has value only through what uses its output. Follow any output forward: if nothing reads it, or only part of it is read, the unread part bought nothing. This happens because the producer usually doesn't know what the consumer will need, so it produces everything to be safe.

**The waste.** Work whose output nobody uses, and the unused part of outputs that are only partly used.

**General directions.**
- **Produce on demand:** wait until something asks for the output.
- **Produce only the part asked for:** let the request say how much is needed.
- **Tell the producer:** pass the consumer's needs back to where the work is done.
- **Stop early:** once the answer is determined, the rest of the work adds nothing.

**Illustrations** (examples only; the best use of this principle may look like none of them). A restaurant cooks to order instead of cooking the whole menu. A search stops at the first match when one is enough. A map loads only the area on the screen.

(card: `02-unused-results.md`)

### Timing

**The principle.** The same work costs different amounts depending on when it is done. At some moments it delays everything that waits on it; at others, capacity is free and nothing is waiting. Every piece of work has a window: it cannot start before its inputs are known, and it must finish before its output is needed. Anywhere inside the window is correct.

**The waste.** Work done at an expensive moment in its window, when a cheaper moment exists.

**General directions.**
- **Do it early:** as soon as the inputs are known, or in a quiet period.
- **Do it late:** after the urgent work, or when more is known; sometimes it turns out not to be needed.
- **Take it off the path others wait on:** the work still happens, but nothing waits for it.
- **Gather it:** hold work until a moment when it is cheap to do together.

**Illustrations** (examples only; the best use of this principle may look like none of them). A chef does the chopping before service starts. A bank settles the day's payments overnight. A shop restocks shelves after closing.

(card: `07-timing.md`)

## This machine: hardware

### How the host learns that the GPU is done

**What it is.** When a host thread waits for GPU work, it can spin on a core, yield its core between checks, or sleep until an interrupt arrives. These differ in how fast the thread reacts and how much processor time it burns. Besides waiting, the host can poll an event without blocking, or attach a function that runs when a stream reaches a given point. The device also reports stream operations that write a value to memory or wait until memory holds a value.

**What it makes possible.** The gap between the GPU finishing and the host acting on it is set by the waiting method, and it is paid at every hand-over.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes). The waiting modes are from the documentation.

**Where to read more.** CUDA Programming Guide: Asynchronous Execution; driver API: context scheduling flags, stream memory operations.

(card: `16-how-the-host-learns-that-the-gpu-is-done.md`)

### Other engines, power and clocks

**What it is.** Besides compute, each GPU has video encoders (two), a video decoder, a JPEG engine and an optical-flow engine; all are idle in a compute program. The compute clock is not fixed: it ranges up to 3,105 MHz and moves with load, temperature and the power limit. The limit is set to 450 W per GPU, and an ordinary user cannot change it.

**What it makes possible.** The same code can run at different speeds at different moments, for reasons outside the code. The engines for video are separate hardware that compute work does not slow down.

**How this was checked.** Read from `nvidia-smi`.

**Where to read more.** `nvidia-smi -q`; NVIDIA Video Codec SDK documentation.

(card: `19-other-engines-power-and-clocks.md`)

### No direct path between the two GPUs

**What it is.** On this machine one GPU cannot read or write the other's memory (peer-to-peer access is reported as not supported), and there is no dedicated GPU-to-GPU link. Data going from one GPU to the other travels up one link into host memory and down the other link. Libraries that depend on direct access between GPUs do not apply here.

**What it makes possible.** Every exchange between the GPUs has two hops and passes through memory the host processors can also see. The host is on the path whether it takes part or not.

**How this was checked.** `nvidia-smi topo -p2p r` reports peer-to-peer as not supported.

**Where to read more.** CUDA Programming Guide: Programming Systems with Multiple GPUs.

(card: `21-no-direct-path-between-the-two-gpus.md`)

### Every transfer has a fixed cost

**What it is.** Moving data across a link costs a fixed amount of time that does not depend on the size: a call into the driver, setting up the transfer, and learning that it has finished. Only above some size does the time grow with the number of bytes.

**What it makes possible.** For small transfers the count matters more than the bytes. The size at which the fixed part stops dominating can be measured, and it tells you which regime a given exchange is in.

**How this was checked.** A general property of this kind of link; the fixed cost on this machine is not stated here. Measure it.

**Where to read more.** CUDA Programming Guide: Asynchronous Execution.

(card: `23-every-transfer-has-a-fixed-cost.md`)

### Graphics hardware a compute program can reach

**What it is.** The chip carries hardware built for graphics that compute code can also use. Texture units fetch from a 1-, 2- or 3-dimensional array and blend the neighbouring entries in hardware in a single fetch (the blend weights have limited precision), with built-in handling of out-of-range coordinates; arrays can be up to 131,072 wide in one dimension. The ray-tracing units search a hierarchy of bounding boxes in hardware; they are reached through a separate library.

**What it makes possible.** A table lookup with interpolation, or a search over spatial data, can be done by dedicated hardware that is otherwise idle in a compute program.

**How this was checked.** Texture limits queried from the device. The ray-tracing path was not checked on this machine.

**Where to read more.** CUDA Programming Guide: texture and surface memory; the OptiX documentation.

(card: `18-graphics-hardware-a-compute-program-can-reach.md`)

## This machine: software

### How Python runs

**What it is.** The Python here is 3.12. One thread at a time executes Python code within an interpreter; the others wait for a lock. Native code called from Python can release the lock while it works, and most heavy library calls do. Separate processes each have their own lock, and so can separate interpreters within one process (in this version they can only be created from native code). Starting a thread is cheap and it shares all memory; a process is isolated and shares only what is arranged.

**What it makes possible.** Whether two pieces of host work truly overlap depends on where the lock is held, not on how many threads exist.

**How this was checked.** Version read from the environment. Whether a given library call releases the lock has to be checked case by case.

**Where to read more.** Python documentation: the global interpreter lock, `threading`, `multiprocessing`.

(card: `09-how-python-runs.md`)

### Ready-made math libraries

**What it is.** NVIDIA's tuned libraries are installed: dense linear algebra (including a lightweight matrix-multiply interface with many formats, and batched forms), sparse linear algebra, matrix multiply with one operand pruned in the fixed pattern the matrix hardware supports, solvers, Fourier transforms, random numbers, the standard deep-learning operations, image and JPEG routines, and reading files directly into GPU memory.

**What it makes possible.** Some of these implement an operation in a way nobody would write by hand, and some expose hardware modes that are otherwise awkward to reach.

**How this was checked.** The packages are installed; which code paths each takes on this chip was not checked.

**Where to read more.** cuBLAS, cuSPARSE, cuSPARSELt, cuSOLVER, cuFFT, cuRAND, cuDNN, NPP, nvJPEG and cuFile documentation.

(card: `05-ready-made-math-libraries.md`)

### Several levels of language for GPU code

**What it is.** GPU code can be written at different levels, and several are installed here. At thread level: CUDA C++ (compiler 13.0) and Numba (Python compiled to the same thing). At block level: Triton, where one program describes a whole thread block and the compiler arranges the threads. At tile level: NVIDIA's CuTe DSL (the building blocks of its matrix-kernel library, usable from Python) and cuTile (kernels written as operations on whole tiles).

**What it makes possible.** The level sets what the author controls and what the compiler decides. The same kernel can be cheap to write at one level and only reach full speed at another, and pieces written at different levels can live in one program.

**How this was checked.** All import in this environment. cuTile's compiler was not run on this chip.

**Where to read more.** CUDA Programming Guide: Writing SIMT Kernels, Writing Tile Kernels; the Triton, Numba, CuTe DSL and cuTile documentation.

(card: `01-several-levels-of-language-for-gpu-code.md`)

### Compiling while the program runs

**What it is.** GPU code does not have to be compiled before the program starts. A program can generate source, compile it in memory (NVRTC), link it with other compiled pieces while still optimizing across them (nvJitLink), and load the result, all while running. The Python kernel languages here work this way already.

**What it makes possible.** At run time the program knows things that were unknown beforehand: sizes, shapes, constants, which case actually occurs. Code compiled then can have them built in.

**How this was checked.** The libraries are installed (NVRTC 13.0, nvJitLink 13.4); not exercised here.

**Where to read more.** NVRTC and nvJitLink documentation; `cuda.core` documentation.

(card: `02-compiling-while-the-program-runs.md`)

### The operating system: what a user cannot control

**What it is.** Some conditions are fixed for an ordinary user. The processor frequency policy raises a core's speed only after load appears on it. The system may move a process's memory pages between the two halves of the host on its own. No cores are reserved: any thread can be interrupted or moved to make room for another, and real-time priority is not available. Other people use the machine. The driver version (580) caps the CUDA version at 13.0. The kernel is Linux 5.15.

**What it makes possible.** These are the conditions any design has to work under. A design that depends on a quiet, pinned, fully warmed-up host will not always get one.

**How this was checked.** Read from `/sys` and `/proc` on this machine.

**Where to read more.** Linux kernel documentation: CPU frequency scaling, NUMA balancing, scheduler.

(card: `12-the-operating-system-what-a-user-cannot-control.md`)
