# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Mismatch with the machine

**The principle.** A machine is not equally good at everything. It has operations and patterns it performs very fast, and others it performs slowly; the difference can be large. The same result can usually be reached through work of different shapes. Speed depends on the fit between the shape of the work and the strengths of the machine, as much as on the amount of work.

**The waste.** Work in a shape the machine does slowly, when an equivalent shape would use what it does fast.

**General directions.**
- **Learn the machine:** what is it fast at, and which of its capabilities are rarely used?
- **Reshape the work:** sizes, order, arrangement, kind of operation, so that it fits.
- **Move work to the part that suits it:** different parts of a machine have different strengths.
- **Ask what is unused:** a capability nobody uses may fit a problem nobody matched it to.

**Illustrations** (examples only; the best use of this principle may look like none of them). Boxes sized to the truck bed fill it with no gaps. A car is efficient only in the right gear. Multiplying by two is a shift for a binary machine.

(card: `17-mismatch-with-the-machine.md`)

### Per-item overhead

**The principle.** The cost of a piece of work often has two parts: one that grows with its size, and a fixed part paid every time regardless of size (setting up, starting, switching, handing over). When items are small, the fixed part dominates. The fixed part belongs to the act of starting, not to the work itself, so several items can share one.

**The waste.** Fixed costs paid more often than necessary.

**General directions.**
- **Group items:** pay the fixed part once for many.
- **Join steps:** let an item pass through several steps without stopping and restarting between them.
- **Stay set up:** keep the preparation between items instead of tearing it down and rebuilding it.
- **Shrink the fixed part:** if it can't be shared, make it cheaper.

**Illustrations** (examples only; the best use of this principle may look like none of them). A bus carries fifty people with one driver. Laundry is done by the load. Goods cross the ocean in containers, not parcel by parcel.

(card: `10-per-item-overhead.md`)

### Idleness

**The principle.** A system is a set of resources, each able to do work at some rate. A job is a set of pieces of work, where some pieces need the results of others. Two things set the minimum time for the job:
- **The longest chain of true dependencies:** pieces that really need each other's results must run one after another.
- **Total work divided by total capacity:** every resource working all the time can't go faster than this.

Any time beyond those two limits is waiting that nothing requires. It usually comes from the order in which the work was arranged, not from what the work needs.

**The waste.** A resource has free capacity, and a piece of work has all its inputs ready, but the work isn't running there.

**General directions.**
- **Separate true dependencies from arranged order:** find which waits are needed and which are only habit.
- **Run ready work on free capacity:** at the same time as other work, or overlapping with it.
- **Shorten the longest chain:** restructure the work so pieces depend on less, or on results that arrive earlier.
- **Move work toward free capacity:** a piece can run on a different resource, even one that does it more slowly, if that resource would otherwise wait.

**Illustrations** (examples only; the best use of this principle may look like none of them). A processor starts the next instruction before the current one finishes. A kitchen prepares side dishes while the main dish is in the oven. A program continues with other work while waiting for a disk read.

(card: `06-idleness.md`)

### Unused results

**The principle.** Work has value only through what uses its output. Follow any output forward: if nothing reads it, or only part of it is read, the unread part bought nothing. This happens because the producer usually doesn't know what the consumer will need, so it produces everything to be safe.

**The waste.** Work whose output nobody uses, and the unused part of outputs that are only partly used.

**General directions.**
- **Produce on demand:** wait until something asks for the output.
- **Produce only the part asked for:** let the request say how much is needed.
- **Tell the producer:** pass the consumer's needs back to where the work is done.
- **Stop early:** once the answer is determined, the rest of the work adds nothing.

**Illustrations** (examples only; the best use of this principle may look like none of them). A restaurant cooks to order instead of cooking the whole menu. A search stops at the first match when one is enough. A map loads only the area on the screen.

(card: `02-unused-results.md`)

### Fixed choices

**The principle.** Many decisions (a size, a limit, an order, a method) are made once, in advance, from a guess about conditions. But conditions vary: between inputs, with load, over time. A fixed choice is right for one condition at most and somewhat wrong for the others. The information needed for a better choice often exists at the moment of use and costs little to observe.

**The waste.** The gap between the fixed choice and the best choice for the conditions that actually occur.

**General directions.**
- **Observe, then choose:** look at the conditions before deciding.
- **Prepare several versions:** and select among them at the moment of use.
- **Adjust by feedback:** measure the result and correct the choice continuously.
- **Decide later:** postpone the decision until more is known.

**Illustrations** (examples only; the best use of this principle may look like none of them). A thermostat replaces a heater that is always on. Traffic lights change their timing with the traffic. A gearbox picks a ratio for the current speed.

(card: `16-fixed-choices.md`)

## This machine: hardware

### Host memory as common ground

**What it is.** Host memory can be pinned (locked in place) and registered with the driver, after which either GPU can copy to and from it directly. The same pinned buffer can serve both GPUs. Memory that already exists, including memory shared between processes, can be registered after the fact, and can be registered read-only. Pinned host memory can also be mapped into a GPU's address space, so a kernel reads or writes it directly, each access crossing the link.

**What it makes possible.** The one place both GPUs can reach is host memory. How that memory is laid out, who writes it and who reads it is open to design.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Unified and System Memory (page-locked host memory).

(card: `24-host-memory-as-common-ground.md`)

### The processor layout

**What it is.** Each GPU has 128 identical processor blocks (SMs). One SM holds up to 1,536 threads (48 groups of 32, called warps) from up to 24 thread blocks. It has 65,536 registers to divide among them (at most 255 per thread) and 100 KB of fast scratch memory (shared memory): 48 KB per thread block by default, up to 99 KB on request. The scratch memory, the first-level cache and the texture cache share one 128 KB pool, and the split can be chosen per kernel.

**What it makes possible.** Registers, scratch memory and thread count trade against each other inside one SM: a kernel that uses fewer registers per thread fits more threads, and one that asks for more scratch memory leaves less first-level cache. A kernel does not have to occupy all 128 SMs.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Compute Capabilities; Ada Tuning Guide.

(card: `01-the-processor-layout.md`)

### The paths between the parts

**What it is.** Each GPU connects to the host by its own PCIe link (generation 4, 16 lanes) on its own port. Both links attach to the first processor socket. A link carries about 32 GB/s in each direction at most. A GPU reads its own memory about 30 times faster than that.

**What it makes possible.** Anything that crosses a link is far more expensive per byte than anything that stays on a GPU. How many bytes cross, and how often, is set by how the work is divided.

**How this was checked.** Topology read from `nvidia-smi` and `lspci`. The link rate is the standard's figure, not a measurement.

**Where to read more.** PCI Express specification summaries; `nvidia-smi topo -m`.

(card: `20-the-paths-between-the-parts.md`)

### Two halves of the host

**What it is.** The host is two halves (NUMA nodes), each a processor with its own memory. A core reaches the other half's memory more slowly than its own. Both GPUs attach to the first half (cores 0-11 and 24-35). A thread on the second half, or a buffer placed in the second half's memory, is one step further from both GPUs.

**What it makes possible.** Where a thread runs and where a buffer lives changes the cost of the same operation.

**How this was checked.** Read from `lscpu`, `nvidia-smi topo -m` and the devices' reported NUMA node.

**Where to read more.** `lscpu`; `/sys/devices/system/node/`.

(card: `27-two-halves-of-the-host.md`)

### How the host learns that the GPU is done

**What it is.** When a host thread waits for GPU work, it can spin on a core, yield its core between checks, or sleep until an interrupt arrives. These differ in how fast the thread reacts and how much processor time it burns. Besides waiting, the host can poll an event without blocking, or attach a function that runs when a stream reaches a given point. The device also reports stream operations that write a value to memory or wait until memory holds a value.

**What it makes possible.** The gap between the GPU finishing and the host acting on it is set by the waiting method, and it is paid at every hand-over.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes). The waiting modes are from the documentation.

**Where to read more.** CUDA Programming Guide: Asynchronous Execution; driver API: context scheduling flags, stream memory operations.

(card: `16-how-the-host-learns-that-the-gpu-is-done.md`)

## This machine: software

### The communication library, beyond one operation

**What it is.** The library that moves data between GPUs (NCCL 2.30) offers more than the sum-across-GPUs operation: broadcast, reduce to one GPU, gather from all, reduce-then-scatter, and plain send and receive between two GPUs. Several operations can be grouped and issued together. Buffers can be registered ahead of time. It has a Python interface. Its newest feature, communication started from inside a kernel, needs direct GPU-to-GPU access and so does not apply on this machine.

**What it makes possible.** The exchange pattern between the GPUs is a choice from a larger set than the one in use, and the library is not the only way to move data.

**How this was checked.** The package and its Python interface are installed. Which transport it selects on this machine was not checked here.

**Where to read more.** NCCL user guide and release notes.

(card: `07-the-communication-library-beyond-one-operation.md`)

### Ready-made math libraries

**What it is.** NVIDIA's tuned libraries are installed: dense linear algebra (including a lightweight matrix-multiply interface with many formats, and batched forms), sparse linear algebra, matrix multiply with one operand pruned in the fixed pattern the matrix hardware supports, solvers, Fourier transforms, random numbers, the standard deep-learning operations, image and JPEG routines, and reading files directly into GPU memory.

**What it makes possible.** Some of these implement an operation in a way nobody would write by hand, and some expose hardware modes that are otherwise awkward to reach.

**How this was checked.** The packages are installed; which code paths each takes on this chip was not checked.

**Where to read more.** cuBLAS, cuSPARSE, cuSPARSELt, cuSOLVER, cuFFT, cuRAND, cuDNN, NPP, nvJPEG and cuFile documentation.

(card: `05-ready-made-math-libraries.md`)

### The framework underneath

**What it is.** The framework keeps its own pool of GPU memory and hands out pieces without asking the driver each time; the pool's behaviour can be tuned and inspected. New operations can be written in C++ or CUDA and loaded as extensions, built ahead of time or when the program starts. The framework exposes streams, events, pinned host memory and non-blocking copies. Each operation passes through a dispatch layer on the host before any GPU work is issued.

**What it makes possible.** The framework's defaults are one arrangement among several it supports, and anything it lacks can be added beside it.

**How this was checked.** From the installed framework (torch 2.14); not exercised here.

**Where to read more.** PyTorch documentation: CUDA semantics, memory management, C++ extensions.

(card: `10-the-framework-underneath.md`)

### How Python runs

**What it is.** The Python here is 3.12. One thread at a time executes Python code within an interpreter; the others wait for a lock. Native code called from Python can release the lock while it works, and most heavy library calls do. Separate processes each have their own lock, and so can separate interpreters within one process (in this version they can only be created from native code). Starting a thread is cheap and it shares all memory; a process is isolated and shares only what is arranged.

**What it makes possible.** Whether two pieces of host work truly overlap depends on where the lock is held, not on how many threads exist.

**How this was checked.** Version read from the environment. Whether a given library call releases the lock has to be checked case by case.

**Where to read more.** Python documentation: the global interpreter lock, `threading`, `multiprocessing`.

(card: `09-how-python-runs.md`)

### Sharing without copying

**What it is.** Several mechanisms let two parties use the same bytes. Host processes can share memory by name (63 GB available in the memory-backed file system). GPU memory can be shared between processes. Libraries in one process can hand each other GPU arrays without a copy through a standard exchange format (DLPack) or a common array interface. Message passing between processes is available with zero-copy for large messages.

**What it makes possible.** A boundary between processes or between libraries does not have to cost a copy.

**How this was checked.** The mechanisms are present in the installed software; not exercised here.

**Where to read more.** DLPack; PyTorch `torch.multiprocessing`; CUDA Programming Guide: Interprocess Communication; ZeroMQ guide.

(card: `08-sharing-without-copying.md`)
