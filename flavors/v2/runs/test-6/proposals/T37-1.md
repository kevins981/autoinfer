# T37-1 (moonshot): one static, row-budgeted step — fill every weight pass

Leader: leader-37. Champion at time of writing: T31-003 (1088.9 tok/s official).
All numbers below are my own measurements on the champion's code (jobs 366-371, 16.2 GPU-min), marked
**measured** (job id) or **assumed**.

## What I measured (the basis)
Unprofiled step timer (python-only logger in `workspaces/t37-log`, 300 prompts, c=16, job 368; 1099.7 tok/s):
- **76% of the run is pure decode steps, 24% is extra time caused by prefill** (15.6 s of 65.1 s). measured (368)
- A decode step is 23.3 ms and the GPU is busy the whole time (idle 0.1-0.2 ms; jobs 366/367). Step time across
  draft depths fits **T = 16.9 ms + 0.10 ms x rows + 0.83 ms x draft steps**: k=1 20.89 ms (32 rows), k=2 23.32 ms
  (48 rows), k=3 25.07 ms (56 rows, 14 seqs; the fit predicts 24.95). measured (368, 369). So **~72% of a decode
  step is a fixed cost** (streaming 12.2 GB of weights per GPU, 128 all-reduce latencies) **shared by only ~37 tokens**.
- Draft acceptance is geometric: position 1 0.774, positions 2 and 3 ~0.72 conditional (0.774 / 0.552 / 0.400 at
  k=3). Tokens per seq-step: k=1 1.78, k=2 2.33, k=3 2.73. measured (369)
- **k=3 is nevertheless slower end to end (1016 vs 1066 tok/s) for a reason unrelated to its merit:** per-request
  recurrent-state pages grow with k (`MambaSpec`: 2 + num_speculative_blocks in align mode), the 5 GiB pool then
  seats only 14 of 16 sequences (also only 19 at max-num-seqs 32), so two requests always wait (TTFT p50 490 ms).
  measured (369, 370). Raising the pool to 5.6 GiB OOMs at startup (49 MiB free). measured (371). The engine is
  capacity-bound on memory: 14.46 GiB model + 5.0 GiB pool + 2.48 GiB of captured CUDA graphs (59 prefill sizes).
- Prefill: each prefill event costs **~15 ms fixed + ~166 us per prompt token** (fit over 185 events, job 368); a
  60-100-token prompt costs a flat ~29 ms. The fixed part is host-side: a prefill-containing step is replayed as 65
  graph pieces with ~1,130 small kernels launched one by one from Python in between (GDN chunk kernels, conv, index
  ops); GPU idle is ~24 ms of a 62 ms step under graph-level tracing (367). The per-token part is ~100 us GEMM
  compute + ~50-70 us of all-reduce bytes over PCIe (node-level kernel sums, 366).
- Things I checked and dropped: FP8 weight bytes have 6.5 bits of entropy per byte (CPU measurement), so lossless
  recoding could save <= 19% of weight traffic at a decode cost in the GEMM inner loop: not worth it. Pipeline
  parallelism doubles weight bytes per token in the memory-bound decode: loses by napkin math.

## The idea
The current design decides a step's rows by request type: exactly k+1 rows per decoding sequence, and prompts
processed as separate, large, compute-bound batches through a different (piecewise-graph + eager) path, with one
captured graph per size. **I reject that.** The dominant cost is the fixed cost of a pass over the weights, so the
engine should run *one* static CUDA graph of R rows (R ~ 80-96, where the champion's register-direct decode GEMM
still applies) every step, and treat rows as a budget spent by expected value:
1. 16 mandatory rows (one per sequence);
2. speculative rows where the chain probability justifies them (deeper k; later allocated per sequence from the
   draft head's confidence), with recurrent-state memory independent of k (the champion already replays GDN state
   from a log instead of snapshotting per draft token);
3. prompt tokens riding as further rows of the same pass (sequential GDN update like decode, same math as decode),
   so a prompt pays the marginal row cost instead of 166 us/token + 15 ms per event, and no Python-launched path
   remains.
One graph instead of ~75 also frees most of the 2.48 GiB of graph memory, which is exactly what deeper
speculation needs.

## Upside (if it fully works): ~+18% over the champion
- Deeper speculation at all 16 sequences: cost model gives k=3 +6.0% and k=4 +7.3% on decode time = **+4.5% /
  +5.5% overall**. assumed (model fitted to measured points up to 56 rows).
- Prefill as rows: removes the fixed 15 ms/event (**4.3% of run time**, measured 368) and prices prompt tokens at
  ~0.10-0.13 ms instead of 0.166 (assumed) = another 4-8%, minus ~2% because a request starts decoding 2-3 steps
  later. **+6-10% overall.**
- Confidence-allocated depth: **+0-5%** (assumed; a toy model says the shared 0.83 ms per draft step eats most of
  it unless acceptance is strongly bimodal).

## Riskiest assumption and cheapest test (milestone 1)
**That the marginal row cost stays ~0.10 ms/row up to 64-96 rows in a static step.** It is measured only to 57
rows and with per-sequence costs mixed in; my sparring partner also singled this out. Counter-evidence I already
have: the 48->57-row segment at 19 sequences cost ~0.2 ms/row (370; includes 3 extra sequences' state and draft
rows), and today's mixed steps at ~105 rows spend +20 ms in the large-M prefill GEMM (366), i.e. the existing
kernels are poor in the 96-200 row range.
Test: make state pages independent of k (or free graph memory) so k=3 and k=4 run with all 16 sequences, then
same-job ABBA vs the champion with the step log: gives T(64) and T(80) directly and the official-style tok/s.
Pass: k=3 or k=4 beats the champion in every pair and T(64), T(80) are within 1 ms of the model (25.8 / 28.2 ms).
Fail (core idea wrong): T grows much faster than 0.10 ms/row beyond 56 rows for a reason tied to hardware
(tensor throughput / PCIe bytes), which would cap both the speculation and the prefill-as-rows gains.

## Roadmap
1. **Depth unlock** (milestone 1 above). Deliverable: a record with k=3/k=4 at 16 seqs, 128K gate tested (memory
   change), official eval if the ABBA wins. Expected +3-5% on its own.
2. **Static mixed step**: prompt chunks as rows of the decode-shaped graph (generalised replay kernel for a
   variable number of rows per sequence; attention metadata as data). First measurement, equal work: elapsed time
   of the mixed pass vs today's separate paths for the same prompt and decode tokens. Then chunk-size policy,
   bitwise/numeric checks vs the chunked prefill path, GSM8K, a different shared prefix for the prefix-cache rule.
3. **Confidence allocation**: log draft confidence vs acceptance (one job), simulate against the measured cost
   curve; implement only if the simulation shows >= 3%.
4. Official eval of the combined record.
