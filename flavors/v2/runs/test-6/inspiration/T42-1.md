# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Distance

**The principle.** Work needs its inputs at the place where it happens. Moving things takes time in proportion to how much is moved and how far, and the paths have limited capacity. Time spent moving is not time spent working. How much movement there is depends on where things are kept and where the work is done, and both are choices.

**The waste.** Movement that a different placement would avoid.

**General directions.**
- **Bring the work to the data:** instead of the data to the work.
- **Keep together what is used together:** so one trip serves many needs.
- **Move less:** only the part that is needed, or a smaller form of it.
- **Move once:** not the same thing back and forth.
- **Keep the most used nearest:** the nearest places are few; give them to what is needed most often.

**Illustrations** (examples only; the best use of this principle may look like none of them). A workshop keeps its most used tools within arm's reach. A retailer puts warehouses near its customers. A question is sent to the database instead of fetching the whole table to answer it.

(card: `09-distance.md`)

### Unused results

**The principle.** Work has value only through what uses its output. Follow any output forward: if nothing reads it, or only part of it is read, the unread part bought nothing. This happens because the producer usually doesn't know what the consumer will need, so it produces everything to be safe.

**The waste.** Work whose output nobody uses, and the unused part of outputs that are only partly used.

**General directions.**
- **Produce on demand:** wait until something asks for the output.
- **Produce only the part asked for:** let the request say how much is needed.
- **Tell the producer:** pass the consumer's needs back to where the work is done.
- **Stop early:** once the answer is determined, the rest of the work adds nothing.

**Illustrations** (examples only; the best use of this principle may look like none of them). A restaurant cooks to order instead of cooking the whole menu. A search stops at the first match when one is enough. A map loads only the area on the screen.

(card: `02-unused-results.md`)

### Repetition

**The principle.** Any piece of work is a function: it takes inputs and produces an output. The output contains nothing that wasn't already determined by the inputs. So work is only necessary when the inputs are new. If the inputs were seen before, the output already exists somewhere. If part of the inputs is new, only the part of the output that depends on it needs to be made.

This holds for computing a value, and equally for moving or storing one: sending something to a place that already has it is the same waste.

**The waste.** The work done, minus the work the new information required.

**General directions.**
- **Remember:** keep an output so the work isn't done again. This trades memory for work.
- **Share:** produce an output once and let everyone who needs it use the same copy.
- **Update by difference:** when the inputs change a little, compute only what the change affects.
- **Do it ahead:** if the inputs are known long before the output is needed, the work can be done once, early.

**Illustrations** (examples only; the best use of this principle may look like none of them). Incremental compilation rebuilds only what a change touched. Rsync sends only the parts of a file the other side lacks. A spreadsheet recomputes only the cells that depend on the edited one.

(card: `01-repetition.md`)

### Unused structure

**The principle.** The cost of work depends on how much the method knows about regularity in its inputs. Data or mathematics with regularity (many zeros, symmetry, sorted order, repeated patterns, few independent directions, operations that may be regrouped) contains less than its size suggests. A method that knows the regularity can do proportionally less.

**The waste.** Work in proportion to the raw size of the problem, when its real content is smaller.

**General directions.**
- **Look for regularity:** measure it; don't assume it is absent.
- **Skip what contributes nothing:** parts known to be zero, unchanged or irrelevant.
- **Do one of a kind:** when parts are symmetric or repeated, do one and reuse it.
- **Use the laws of the mathematics:** regroup, factor or reorder to reach a cheaper equivalent form.
- **Choose a method whose cost follows the content:** not the size.

**Illustrations** (examples only; the best use of this principle may look like none of them). Sorted order lets you find a name in a phone book in a few steps. Multiplying by a table that is mostly zeros needs only the non-zero entries. Gauss summed 1 to 100 by pairing the ends.

(card: `04-unused-structure.md`)

### Fixed choices

**The principle.** Many decisions (a size, a limit, an order, a method) are made once, in advance, from a guess about conditions. But conditions vary: between inputs, with load, over time. A fixed choice is right for one condition at most and somewhat wrong for the others. The information needed for a better choice often exists at the moment of use and costs little to observe.

**The waste.** The gap between the fixed choice and the best choice for the conditions that actually occur.

**General directions.**
- **Observe, then choose:** look at the conditions before deciding.
- **Prepare several versions:** and select among them at the moment of use.
- **Adjust by feedback:** measure the result and correct the choice continuously.
- **Decide later:** postpone the decision until more is known.

**Illustrations** (examples only; the best use of this principle may look like none of them). A thermostat replaces a heater that is always on. Traffic lights change their timing with the traffic. A gearbox picks a ratio for the current speed.

(card: `16-fixed-choices.md`)

## This machine: hardware

### Work described ahead of time as a graph

**What it is.** A sequence of kernels and copies, with their dependencies, can be recorded once as a graph and then launched as a unit, any number of times. Parameters of individual nodes can be updated without rebuilding the graph. Graphs can contain conditional nodes (if, while, switch) whose condition is written by a kernel on the GPU, so a decision does not have to go back to the host. A kernel can itself launch a graph.

**What it makes possible.** The cost of issuing many small pieces of work is paid once, and some control flow can stay on the GPU.

**How this was checked.** From the documentation; conditional nodes and device-side launch were not tried on this machine.

**Where to read more.** CUDA Programming Guide: CUDA Graphs.

(card: `15-work-described-ahead-of-time-as-a-graph.md`)

### Host memory as common ground

**What it is.** Host memory can be pinned (locked in place) and registered with the driver, after which either GPU can copy to and from it directly. The same pinned buffer can serve both GPUs. Memory that already exists, including memory shared between processes, can be registered after the fact, and can be registered read-only. Pinned host memory can also be mapped into a GPU's address space, so a kernel reads or writes it directly, each access crossing the link.

**What it makes possible.** The one place both GPUs can reach is host memory. How that memory is laid out, who writes it and who reads it is open to design.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Unified and System Memory (page-locked host memory).

(card: `24-host-memory-as-common-ground.md`)

### Other engines, power and clocks

**What it is.** Besides compute, each GPU has video encoders (two), a video decoder, a JPEG engine and an optical-flow engine; all are idle in a compute program. The compute clock is not fixed: it ranges up to 3,105 MHz and moves with load, temperature and the power limit. The limit is set to 450 W per GPU, and an ordinary user cannot change it.

**What it makes possible.** The same code can run at different speeds at different moments, for reasons outside the code. The engines for video are separate hardware that compute work does not slow down.

**How this was checked.** Read from `nvidia-smi`.

**Where to read more.** `nvidia-smi -q`; NVIDIA Video Codec SDK documentation.

(card: `19-other-engines-power-and-clocks.md`)

### Matrix hardware: the data types it accepts

**What it is.** The matrix-multiply units (tensor cores) work on small fixed tiles, one warp at a time. On this chip they accept: 16-bit float, bfloat16, a 19-bit float (TF32), 64-bit float, 8-bit and 4-bit integers, single bits (with XOR or AND followed by a bit count), and two 8-bit float formats (E4M3 and E5M2, which can be mixed in one product). The 8-bit floats accumulate in 32-bit float. Tile depth grows as the type shrinks: 16 for the 16-bit floats, 32 for 8-bit types, 64 for 4-bit, 256 for single bits. There is a sparse form in which one operand has half its values removed in a fixed pattern. Single instructions convert pairs of 32-bit floats to and from the 8-bit float formats.

**What it makes possible.** The same matrix hardware does several times more multiplies per instruction on narrower types, and narrower operands are also fewer bytes to fetch.

**How this was checked.** Each instruction was assembled for this chip (`ptxas -arch=sm_89`); not run.

**Where to read more.** PTX ISA reference: warp-level matrix instructions (`mma`, `mma.sp`), `cvt`.

(card: `02-matrix-hardware-the-data-types-it-accepts.md`)

### The processor layout

**What it is.** Each GPU has 128 identical processor blocks (SMs). One SM holds up to 1,536 threads (48 groups of 32, called warps) from up to 24 thread blocks. It has 65,536 registers to divide among them (at most 255 per thread) and 100 KB of fast scratch memory (shared memory): 48 KB per thread block by default, up to 99 KB on request. The scratch memory, the first-level cache and the texture cache share one 128 KB pool, and the split can be chosen per kernel.

**What it makes possible.** Registers, scratch memory and thread count trade against each other inside one SM: a kernel that uses fewer registers per thread fits more threads, and one that asks for more scratch memory leaves less first-level cache. A kernel does not have to occupy all 128 SMs.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Compute Capabilities; Ada Tuning Guide.

(card: `01-the-processor-layout.md`)

## This machine: software

### Several levels of language for GPU code

**What it is.** GPU code can be written at different levels, and several are installed here. At thread level: CUDA C++ (compiler 13.0) and Numba (Python compiled to the same thing). At block level: Triton, where one program describes a whole thread block and the compiler arranges the threads. At tile level: NVIDIA's CuTe DSL (the building blocks of its matrix-kernel library, usable from Python) and cuTile (kernels written as operations on whole tiles).

**What it makes possible.** The level sets what the author controls and what the compiler decides. The same kernel can be cheap to write at one level and only reach full speed at another, and pieces written at different levels can live in one program.

**How this was checked.** All import in this environment. cuTile's compiler was not run on this chip.

**Where to read more.** CUDA Programming Guide: Writing SIMT Kernels, Writing Tile Kernels; the Triton, Numba, CuTe DSL and cuTile documentation.

(card: `01-several-levels-of-language-for-gpu-code.md`)

### Compiling while the program runs

**What it is.** GPU code does not have to be compiled before the program starts. A program can generate source, compile it in memory (NVRTC), link it with other compiled pieces while still optimizing across them (nvJitLink), and load the result, all while running. The Python kernel languages here work this way already.

**What it makes possible.** At run time the program knows things that were unknown beforehand: sizes, shapes, constants, which case actually occurs. Code compiled then can have them built in.

**How this was checked.** The libraries are installed (NVRTC 13.0, nvJitLink 13.4); not exercised here.

**Where to read more.** NVRTC and nvJitLink documentation; `cuda.core` documentation.

(card: `02-compiling-while-the-program-runs.md`)

### Parallel building blocks

**What it is.** A library of general parallel algorithms for the GPU is installed, in C++ and with a Python interface: sort, scan (running totals), reduce, select the items that meet a condition, partition, remove duplicates, histogram, run-length encode, search, merge.

**What it makes possible.** Problems that look inherently sequential, such as compacting a list or grouping equal items, have well-known parallel forms that are already written.

**How this was checked.** The package is installed (CCCL 13.3); not exercised here.

**Where to read more.** CCCL documentation (Thrust, CUB, `cuda.cccl`).

(card: `06-parallel-building-blocks.md`)

### Down to the instructions

**What it is.** The compiler's intermediate language (PTX) can be read, written by hand, and placed inline inside C++ code. The assembler reports registers used and spilled per kernel. The final machine instructions can be disassembled from any compiled kernel, including ones from libraries. The profiler can attribute time to single source lines and instructions.

**What it makes possible.** What a kernel really does is visible, and what the higher-level languages do not expose can still be written.

**How this was checked.** The tools are installed (`ptxas`, `nvdisasm`, `cuobjdump`) and the assembler was used to check the hardware cards.

**Where to read more.** PTX ISA reference; CUDA binary utilities documentation.

(card: `03-down-to-the-instructions.md`)

### How Python runs

**What it is.** The Python here is 3.12. One thread at a time executes Python code within an interpreter; the others wait for a lock. Native code called from Python can release the lock while it works, and most heavy library calls do. Separate processes each have their own lock, and so can separate interpreters within one process (in this version they can only be created from native code). Starting a thread is cheap and it shares all memory; a process is isolated and shares only what is arranged.

**What it makes possible.** Whether two pieces of host work truly overlap depends on where the lock is held, not on how many threads exist.

**How this was checked.** Version read from the environment. Whether a given library call releases the lock has to be checked case by case.

**Where to read more.** Python documentation: the global interpreter lock, `threading`, `multiprocessing`.

(card: `09-how-python-runs.md`)
