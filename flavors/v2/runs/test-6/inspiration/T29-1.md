# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Predictability

**The principle.** Waiting for a result is necessary only if the result can't be predicted. If a guess is usually right, and checking a guess costs less than waiting for the answer, work can go ahead on the guess and be corrected in the rare cases it was wrong. The gain is roughly (chance of being right x time saved) - (chance of being wrong x work wasted). It needs three things: a cheap guess, a cheap check, and a way to undo.

**The waste.** Time spent waiting for an answer that was largely known in advance.

**General directions.**
- **Guess and verify:** proceed on the likely answer; check it when the real one arrives.
- **Prepare ahead:** get ready what is likely to be needed next.
- **Follow several possibilities:** and keep the one that turns out right.
- **Improve the odds or lower the price:** a better guess, a cheaper check, or a cheaper undo.

**Illustrations** (examples only; the best use of this principle may look like none of them). A processor guesses which way a branch will go and runs ahead. A waiter starts a regular's usual order when they walk in. A disk reads the next blocks before they are asked for.

(card: `08-predictability.md`)

### Mismatch with the machine

**The principle.** A machine is not equally good at everything. It has operations and patterns it performs very fast, and others it performs slowly; the difference can be large. The same result can usually be reached through work of different shapes. Speed depends on the fit between the shape of the work and the strengths of the machine, as much as on the amount of work.

**The waste.** Work in a shape the machine does slowly, when an equivalent shape would use what it does fast.

**General directions.**
- **Learn the machine:** what is it fast at, and which of its capabilities are rarely used?
- **Reshape the work:** sizes, order, arrangement, kind of operation, so that it fits.
- **Move work to the part that suits it:** different parts of a machine have different strengths.
- **Ask what is unused:** a capability nobody uses may fit a problem nobody matched it to.

**Illustrations** (examples only; the best use of this principle may look like none of them). Boxes sized to the truck bed fill it with no gaps. A car is efficient only in the right gear. Multiplying by two is a shift for a binary machine.

(card: `17-mismatch-with-the-machine.md`)

### Overqualified work

**The principle.** Expensive work is often applied to many candidates, of which only a few matter to the final answer. If a cheap test can tell which candidates cannot matter, the expensive work is needed only for the rest. The final answer still comes from the expensive, exact work, so it stays exact. The cheap test only has to avoid ruling out a candidate that matters.

**The waste.** Exact work spent on candidates that a cheaper test would have eliminated.

**General directions.**
- **Cheap pass first:** then exact work on the survivors only.
- **Use bounds:** a cheap bound can prove a candidate cannot win without evaluating it.
- **Stages of rising cost:** each stage removes candidates before the next, dearer one.
- **Order the tests:** cheapest and most selective first.

**Illustrations** (examples only; the best use of this principle may look like none of them). Security screens everyone quickly and searches a few by hand. An index rules out most rows before any is read. A chess program drops moves that a bound shows cannot beat the best found so far.

(card: `05-overqualified-work.md`)

### Generality

**The principle.** Work that can handle many cases has to find out which case it is in, and has to be built so that every case stays possible. The more that is known in advance about the inputs, the less there is to decide and the less work remains. Every fact that is fixed in this situation (a size, a type, a range, a condition that always holds) is a decision that could be made once, ahead of time, instead of every time.

**The waste.** Checks, indirection and cautious choices that exist for cases which never occur here.

**General directions.**
- **Fix what is known:** build a version for the case that actually occurs.
- **Remove decisions with one answer:** a check that always comes out the same isn't a check.
- **Use a narrower method:** one that only works under the conditions that hold here can be cheaper.
- **Keep the general version as a fallback:** the special version only needs to cover what it was built for.

**Illustrations** (examples only; the best use of this principle may look like none of them). A key fits one lock; a locksmith's toolkit opens any, slowly. A compiler replaces a calculation on constants with its result. A production line built for one product outruns a general workshop.

(card: `03-generality.md`)

### Boundaries

**The principle.** Systems are divided into parts so that each can be built and understood on its own. Every boundary has two costs:
- **Crossing:** things are converted, copied, checked and handed over.
- **Blindness:** each part decides with only what it can see. It can't use what its neighbours know, so it must assume the worst.

**The waste.** The cost of crossing, plus the better decisions missed because knowledge stops at the boundary.

**General directions.**
- **Pass knowledge across:** tell the other side what you know, so it needn't assume or rediscover it.
- **Merge parts:** that work on the same thing.
- **Go around a layer:** when the service it provides isn't needed on this path.
- **Move the boundary:** to where fewer things cross it.

**Illustrations** (examples only; the best use of this principle may look like none of them). Two people who share a language need no interpreter. A form that passes through five departments waits at each desk. A compiler that sees across a function call can simplify both sides.

(card: `11-boundaries.md`)

## This machine: hardware

### The processor layout

**What it is.** Each GPU has 128 identical processor blocks (SMs). One SM holds up to 1,536 threads (48 groups of 32, called warps) from up to 24 thread blocks. It has 65,536 registers to divide among them (at most 255 per thread) and 100 KB of fast scratch memory (shared memory): 48 KB per thread block by default, up to 99 KB on request. The scratch memory, the first-level cache and the texture cache share one 128 KB pool, and the split can be chosen per kernel.

**What it makes possible.** Registers, scratch memory and thread count trade against each other inside one SM: a kernel that uses fewer registers per thread fits more threads, and one that asks for more scratch memory leaves less first-level cache. A kernel does not have to occupy all 128 SMs.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Compute Capabilities; Ada Tuning Guide.

(card: `01-the-processor-layout.md`)

### More than one kernel at a time

**What it is.** A GPU can have up to 128 kernels resident at once. Kernels issued on different streams of one process may run at the same time when the first leaves SMs, registers or scratch memory free; otherwise they run one after another. Streams can be given priorities. The two GPUs are fully independent of each other.

**What it makes possible.** A small kernel does not have to wait behind a large one, and a kernel that cannot use the whole chip need not leave the rest idle.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Asynchronous Execution.

(card: `12-more-than-one-kernel-at-a-time.md`)

### Copy engines beside the compute engine

**What it is.** Each GPU reports two copy engines, separate from the hardware that runs kernels. A copy between host and GPU can proceed while a kernel runs, and a copy in each direction can proceed at the same time.

**What it makes possible.** Moving data on or off a GPU does not have to stop computation on it, and sending does not have to wait for receiving.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Asynchronous Execution.

(card: `17-copy-engines-beside-the-compute-engine.md`)

### Single instructions that do a loop's work

**What it is.** The instruction set has single instructions for jobs that are usually written as loops or several steps: count the set bits in a word, find the highest set bit, reverse bits, extract or insert a bit field; any three-input boolean function; a four-way 8-bit dot product into a 32-bit sum; reduce a value across all 32 threads of a warp (sum, min, max, and, or, xor); find which threads of a warp hold the same value; packed pairs of 16-bit floats in one register, with a fused multiply-add that can clamp at zero; an approximate tanh.

**What it makes possible.** Work on bits, small integers and whole warps can cost one instruction where a straightforward version costs many, and can stay in registers without touching memory.

**How this was checked.** Each instruction was assembled for this chip (`ptxas -arch=sm_89`); not run.

**Where to read more.** PTX ISA reference: integer, logic and warp-level instructions; CUDA Programming Guide: Device-Callable APIs and Intrinsics.

(card: `04-single-instructions-that-do-a-loop-s-work.md`)

### The host processors

**What it is.** Two Intel Xeon Silver 4410Y processors: 12 cores each (24 cores, 48 hardware threads), 2.0 GHz base and up to 3.9 GHz. Each core has 2 MiB of second-level cache; each processor has 30 MiB of third-level cache. They have 512-bit vector instructions, including 16-bit float and bfloat16 arithmetic and 8-bit integer dot products, and a matrix extension (AMX) that multiplies tiles of bfloat16 or 8-bit integers.

**What it makes possible.** The host is slow next to a GPU but far from negligible, it is mostly idle while the GPUs work, and it sits on the path between them.

**How this was checked.** Read from `lscpu`.

**Where to read more.** Intel's processor specification page; Intel intrinsics guide.

(card: `26-the-host-processors.md`)

## This machine: software

### Compiling while the program runs

**What it is.** GPU code does not have to be compiled before the program starts. A program can generate source, compile it in memory (NVRTC), link it with other compiled pieces while still optimizing across them (nvJitLink), and load the result, all while running. The Python kernel languages here work this way already.

**What it makes possible.** At run time the program knows things that were unknown beforehand: sizes, shapes, constants, which case actually occurs. Code compiled then can have them built in.

**How this was checked.** The libraries are installed (NVRTC 13.0, nvJitLink 13.4); not exercised here.

**Where to read more.** NVRTC and nvJitLink documentation; `cuda.core` documentation.

(card: `02-compiling-while-the-program-runs.md`)

### How Python runs

**What it is.** The Python here is 3.12. One thread at a time executes Python code within an interpreter; the others wait for a lock. Native code called from Python can release the lock while it works, and most heavy library calls do. Separate processes each have their own lock, and so can separate interpreters within one process (in this version they can only be created from native code). Starting a thread is cheap and it shares all memory; a process is isolated and shares only what is arranged.

**What it makes possible.** Whether two pieces of host work truly overlap depends on where the lock is held, not on how many threads exist.

**How this was checked.** Version read from the environment. Whether a given library call releases the lock has to be checked case by case.

**Where to read more.** Python documentation: the global interpreter lock, `threading`, `multiprocessing`.

(card: `09-how-python-runs.md`)

### Compiling a whole sequence of operations as one

**What it is.** The framework can trace a model's sequence of operations and hand it to a compiler as one unit, which may fuse operations, drop intermediate results and generate code specialized to the shapes seen. Separately, a sequence of GPU operations can be captured once and replayed as a graph.

**What it makes possible.** Boundaries between operations are a choice of the code as written, not of the computation.

**How this was checked.** Part of the installed framework (torch 2.14); not exercised here.

**Where to read more.** PyTorch documentation: `torch.compile`, `torch.fx`, CUDA graphs.

(card: `04-compiling-a-whole-sequence-of-operations-as-one.md`)

### Parallel building blocks

**What it is.** A library of general parallel algorithms for the GPU is installed, in C++ and with a Python interface: sort, scan (running totals), reduce, select the items that meet a condition, partition, remove duplicates, histogram, run-length encode, search, merge.

**What it makes possible.** Problems that look inherently sequential, such as compacting a list or grouping equal items, have well-known parallel forms that are already written.

**How this was checked.** The package is installed (CCCL 13.3); not exercised here.

**Where to read more.** CCCL documentation (Thrust, CUB, `cuda.cccl`).

(card: `06-parallel-building-blocks.md`)

### The communication library, beyond one operation

**What it is.** The library that moves data between GPUs (NCCL 2.30) offers more than the sum-across-GPUs operation: broadcast, reduce to one GPU, gather from all, reduce-then-scatter, and plain send and receive between two GPUs. Several operations can be grouped and issued together. Buffers can be registered ahead of time. It has a Python interface. Its newest feature, communication started from inside a kernel, needs direct GPU-to-GPU access and so does not apply on this machine.

**What it makes possible.** The exchange pattern between the GPUs is a choice from a larger set than the one in use, and the library is not the only way to move data.

**How this was checked.** The package and its Python interface are installed. Which transport it selects on this machine was not checked here.

**Where to read more.** NCCL user guide and release notes.

(card: `07-the-communication-library-beyond-one-operation.md`)
