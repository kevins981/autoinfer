**#1 is plausible, but B.2 overstates how much of the slot contract it preserves. #2 is valid in principle and potentially graph-capturable; its gain estimate is too optimistic.** These are code/profile findings; I ran no GPU work.

1. **Row 0 is committed, but its state is not necessarily the final accepted state.**

   For a live decode request, row 0 is the previously sampled token; rejection applies to the following draft inputs. With inputs `[x, d1, d2]`, the required continuation state is:

   | Accepted output count `a` | Required state |
   |---|---|
   | 1 | after `x` |
   | 2 | after `x, d1` |
   | 3 | after `x, d1, d2` |

   The replacement/bonus output has **not** yet passed through the recurrence. This matches the existing `state_indices[a-1]` load at [fused_gdn_decode_kernel.cu:174](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t5-champ/vllm/csrc/gdn/fused_gdn_decode_kernel.cu:174), the rejection sampler at `vllm/v1/sample/rejection_sampler.py:821`, and accepted-count production at `vllm/v1/worker/gpu_model_runner.py:1598`.

   Thus **checkpoint-after-row-0 plus replay of `a-1` rows is sound for ordinary continuation**. “After row 0 is final” should become “after row 0 is an irrevocably committed checkpoint.”

3. **Lifecycle cases that must be explicit in the design:**

   - **First decode after prefill / prefix hit:** slot 0 holds a materialized prefill/prefix state, with neutral count 1. Replay zero rows; ignore stale log bytes. Prefill must establish this invariant.
   - **Align pre-copy:** materialize the previous accepted state into the new running block **before** resetting the count to 1 (`v1/worker/mamba_utils.py:1621`).
   - **Align postprocess:** same-block copies can overwrite the checkpoint and reset the count to 1 (`v1/worker/mamba_utils.py:475`). Use the original count snapshot, and ensure the resulting checkpoint has no pending replay. Do not independently reset this shared count: convolution uses it too (`qwen_gdn_linear_attn.py:2333`).
   - **Preemption, resume, finished requests, slot reuse:** initialize/invalidate log ownership with the request’s state, not its batch-row number. New/resumed batch entries reset counts (`gpu_input_batch.py:462`); stale running-block trackers are removed at `v1/worker/mamba_utils.py:1493`.
   - **Padding / shortened verification:** preserve zero-length and NULL-slot guards. CUDA returns before state access at lines 170/179; padded metadata contains NULL slots, repeated sequence ends and count 1 (`gdn_attn.py:637, 662, 669`). Never replay merely because stale log bytes exist.
   - **Mixed steps:** decode-only changes cannot safely coexist with unchanged mixed-step consumers across successive iterations. Routing speculative rows through CUDA requires gathering/scattering their gates and outputs as well as qkv/a/b; the current fused route explicitly excludes prefills (`qwen_gdn_linear_attn.py:2484`).

4. **Bitwise replay is achievable for this FP32 CUDA recurrence, with strict conditions.**

   Log normalized **FP32** keys, exact decay/beta and losslessly retained values; preserve the multiply, four-element accumulation, XOR shuffle reduction and FMA order at [fused_gdn_decode_kernel.cu:283](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t5-champ/vllm/csrc/gdn/fused_gdn_decode_kernel.cu:283). BF16-normalized keys or a generic Triton reduction do not establish bitwise identity.

   A useful refinement is to log **FP32 decay, normalized key and the already-computed delta vector** from line 301. Replay then needs only the original decay and rank-one update, avoiding the state/key reduction. That is roughly 1 KB/head/row. Mixed-path Triton compatibility still requires its own numerical argument; moving those rows to CUDA changes floating-point ordering.

5. **#2: valid row decomposition, but fix the pipeline cost and capture plan.**

   The proposed sites are row-independent: `RowParallelLinear.forward` performs local GEMM then AR (`vllm/model_executor/layers/linear.py:1844`). Per-token-group quantization also permits row splitting, provided both activation codes **and scales** are sliced (`BlockScaledMMLinearKernel.py:139`).

   Capture is feasible using persistent streams/events and one opaque operator enclosing the fork/join. This tree already has that stream/event pattern (`vllm/utils/multi_stream_utils.py:124`), and PyNCCL accepts an explicit/current stream (`pynccl.py:273`). Keep collective order identical across ranks, serialize both ARs on one communication stream, and join before downstream consumers. A plain Python stream block inserted into compiled model code is not sufficient proof of capture.

   Price the actual pipeline:

   `G1 + max(AR1, G2) + AR2`

   against `G(full) + AR(full)`. You add a collective latency, only overlap **AR1**, and can worsen GEMM efficiency. Smaller chunks may also switch to HMAR automatically (`cuda_communicator.py:430`). “Two halves exceed ridge” does not guarantee unchanged total GEMM time.

   Finally, multiplying savings by all 371 mixed steps is inconsistent with the threshold: your graph trace has only **27/52** mixed steps with total rows ≥192, and **25/52** ≥300. Rank #2 as a worthwhile microbenchmark, with unproven end-to-end upside.
