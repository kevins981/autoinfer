# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Excess guarantees

**The principle.** Every part of a system makes promises to whatever uses it: about order, exactness, freshness, completeness, timing. Each promise costs work to keep. Promises are usually set strong, because strong is safe and the users' real needs weren't known. Often what the users actually rely on is weaker.

The promises a system makes to the outside world are set by its requirements. The promises its parts make to each other are choices.

**The waste.** Work spent keeping a promise nobody relies on.

**General directions.**
- **Ask who relies on it:** for each promise, find what would break without it.
- **Weaken what nobody relies on:** while keeping everything the outside depends on.
- **Keep it only where it matters:** at the points or moments where it is relied on.
- **Keep it more cheaply:** the same promise, delivered by a different mechanism.

**Illustrations** (examples only; the best use of this principle may look like none of them). Not every letter needs registered mail. A bank need not post each payment the instant it is made. A list need not be fully sorted to find its largest entry.

(card: `18-excess-guarantees.md`)

### Skew

**The principle.** Costs are rarely spread evenly. A few cases, items or paths usually account for most of the total. Treating everything the same means designing for an average that hardly occurs: the frequent few get no special care, and the rare many get more than they need.

**The waste.** Uniform treatment of unequal things.

**General directions.**
- **Measure the distribution:** find which few account for most.
- **Make the frequent case cheap:** even if the rare case gets slower.
- **Give the best places to the most used:** the fastest, nearest or shortest.
- **Handle the rare cases apart:** simply, without burdening the common path.

**Illustrations** (examples only; the best use of this principle may look like none of them). Morse code gives the most common letter a single dot. A supermarket opens an express lane. The most used items in a kitchen sit at hand height.

(card: `15-skew.md`)

### Mismatch with the machine

**The principle.** A machine is not equally good at everything. It has operations and patterns it performs very fast, and others it performs slowly; the difference can be large. The same result can usually be reached through work of different shapes. Speed depends on the fit between the shape of the work and the strengths of the machine, as much as on the amount of work.

**The waste.** Work in a shape the machine does slowly, when an equivalent shape would use what it does fast.

**General directions.**
- **Learn the machine:** what is it fast at, and which of its capabilities are rarely used?
- **Reshape the work:** sizes, order, arrangement, kind of operation, so that it fits.
- **Move work to the part that suits it:** different parts of a machine have different strengths.
- **Ask what is unused:** a capability nobody uses may fit a problem nobody matched it to.

**Illustrations** (examples only; the best use of this principle may look like none of them). Boxes sized to the truck bed fill it with no gaps. A car is efficient only in the right gear. Multiplying by two is a shift for a binary machine.

(card: `17-mismatch-with-the-machine.md`)

### Predictability

**The principle.** Waiting for a result is necessary only if the result can't be predicted. If a guess is usually right, and checking a guess costs less than waiting for the answer, work can go ahead on the guess and be corrected in the rare cases it was wrong. The gain is roughly (chance of being right x time saved) - (chance of being wrong x work wasted). It needs three things: a cheap guess, a cheap check, and a way to undo.

**The waste.** Time spent waiting for an answer that was largely known in advance.

**General directions.**
- **Guess and verify:** proceed on the likely answer; check it when the real one arrives.
- **Prepare ahead:** get ready what is likely to be needed next.
- **Follow several possibilities:** and keep the one that turns out right.
- **Improve the odds or lower the price:** a better guess, a cheaper check, or a cheaper undo.

**Illustrations** (examples only; the best use of this principle may look like none of them). A processor guesses which way a branch will go and runs ahead. A waiter starts a regular's usual order when they walk in. A disk reads the next blocks before they are asked for.

(card: `08-predictability.md`)

### Repetition

**The principle.** Any piece of work is a function: it takes inputs and produces an output. The output contains nothing that wasn't already determined by the inputs. So work is only necessary when the inputs are new. If the inputs were seen before, the output already exists somewhere. If part of the inputs is new, only the part of the output that depends on it needs to be made.

This holds for computing a value, and equally for moving or storing one: sending something to a place that already has it is the same waste.

**The waste.** The work done, minus the work the new information required.

**General directions.**
- **Remember:** keep an output so the work isn't done again. This trades memory for work.
- **Share:** produce an output once and let everyone who needs it use the same copy.
- **Update by difference:** when the inputs change a little, compute only what the change affects.
- **Do it ahead:** if the inputs are known long before the output is needed, the work can be done once, early.

**Illustrations** (examples only; the best use of this principle may look like none of them). Incremental compilation rebuilds only what a change touched. Rsync sends only the parts of a file the other side lacks. A spreadsheet recomputes only the cells that depend on the edited one.

(card: `01-repetition.md`)

## This machine: hardware

### Host memory

**What it is.** 125 GB of DDR5 memory across the two halves, shared with other users. The processors support 8 memory channels each at up to 4,000 MT/s; how many are populated was not checked. Host memory is slower to read than GPU memory (how much slower was not measured), but there is five times as much of it as one GPU has. A memory-backed file system (`/dev/shm`, 63 GB) lets processes share memory by name.

**What it makes possible.** The host has room to hold things the GPUs cannot, at the cost of the link to reach them.

**How this was checked.** Sizes read from `free` and `df`. Memory speed was not measured.

**Where to read more.** `lscpu`, `dmidecode` output where readable without root.

(card: `28-host-memory.md`)

### The processor layout

**What it is.** Each GPU has 128 identical processor blocks (SMs). One SM holds up to 1,536 threads (48 groups of 32, called warps) from up to 24 thread blocks. It has 65,536 registers to divide among them (at most 255 per thread) and 100 KB of fast scratch memory (shared memory): 48 KB per thread block by default, up to 99 KB on request. The scratch memory, the first-level cache and the texture cache share one 128 KB pool, and the split can be chosen per kernel.

**What it makes possible.** Registers, scratch memory and thread count trade against each other inside one SM: a kernel that uses fewer registers per thread fits more threads, and one that asks for more scratch memory leaves less first-level cache. A kernel does not have to occupy all 128 SMs.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Compute Capabilities; Ada Tuning Guide.

(card: `01-the-processor-layout.md`)

### Matrix hardware: the data types it accepts

**What it is.** The matrix-multiply units (tensor cores) work on small fixed tiles, one warp at a time. On this chip they accept: 16-bit float, bfloat16, a 19-bit float (TF32), 64-bit float, 8-bit and 4-bit integers, single bits (with XOR or AND followed by a bit count), and two 8-bit float formats (E4M3 and E5M2, which can be mixed in one product). The 8-bit floats accumulate in 32-bit float. Tile depth grows as the type shrinks: 16 for the 16-bit floats, 32 for 8-bit types, 64 for 4-bit, 256 for single bits. There is a sparse form in which one operand has half its values removed in a fixed pattern. Single instructions convert pairs of 32-bit floats to and from the 8-bit float formats.

**What it makes possible.** The same matrix hardware does several times more multiplies per instruction on narrower types, and narrower operands are also fewer bytes to fetch.

**How this was checked.** Each instruction was assembled for this chip (`ptxas -arch=sm_89`); not run.

**Where to read more.** PTX ISA reference: warp-level matrix instructions (`mma`, `mma.sp`), `cvt`.

(card: `02-matrix-hardware-the-data-types-it-accepts.md`)

### No direct path between the two GPUs

**What it is.** On this machine one GPU cannot read or write the other's memory (peer-to-peer access is reported as not supported), and there is no dedicated GPU-to-GPU link. Data going from one GPU to the other travels up one link into host memory and down the other link. Libraries that depend on direct access between GPUs do not apply here.

**What it makes possible.** Every exchange between the GPUs has two hops and passes through memory the host processors can also see. The host is on the path whether it takes part or not.

**How this was checked.** `nvidia-smi topo -p2p r` reports peer-to-peer as not supported.

**Where to read more.** CUDA Programming Guide: Programming Systems with Multiple GPUs.

(card: `21-no-direct-path-between-the-two-gpus.md`)

### Host memory as common ground

**What it is.** Host memory can be pinned (locked in place) and registered with the driver, after which either GPU can copy to and from it directly. The same pinned buffer can serve both GPUs. Memory that already exists, including memory shared between processes, can be registered after the fact, and can be registered read-only. Pinned host memory can also be mapped into a GPU's address space, so a kernel reads or writes it directly, each access crossing the link.

**What it makes possible.** The one place both GPUs can reach is host memory. How that memory is laid out, who writes it and who reads it is open to design.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Unified and System Memory (page-locked host memory).

(card: `24-host-memory-as-common-ground.md`)

## This machine: software

### Ready-made math libraries

**What it is.** NVIDIA's tuned libraries are installed: dense linear algebra (including a lightweight matrix-multiply interface with many formats, and batched forms), sparse linear algebra, matrix multiply with one operand pruned in the fixed pattern the matrix hardware supports, solvers, Fourier transforms, random numbers, the standard deep-learning operations, image and JPEG routines, and reading files directly into GPU memory.

**What it makes possible.** Some of these implement an operation in a way nobody would write by hand, and some expose hardware modes that are otherwise awkward to reach.

**How this was checked.** The packages are installed; which code paths each takes on this chip was not checked.

**Where to read more.** cuBLAS, cuSPARSE, cuSPARSELt, cuSOLVER, cuFFT, cuRAND, cuDNN, NPP, nvJPEG and cuFile documentation.

(card: `05-ready-made-math-libraries.md`)

### Down to the instructions

**What it is.** The compiler's intermediate language (PTX) can be read, written by hand, and placed inline inside C++ code. The assembler reports registers used and spilled per kernel. The final machine instructions can be disassembled from any compiled kernel, including ones from libraries. The profiler can attribute time to single source lines and instructions.

**What it makes possible.** What a kernel really does is visible, and what the higher-level languages do not expose can still be written.

**How this was checked.** The tools are installed (`ptxas`, `nvdisasm`, `cuobjdump`) and the assembler was used to check the hardware cards.

**Where to read more.** PTX ISA reference; CUDA binary utilities documentation.

(card: `03-down-to-the-instructions.md`)

### The operating system: what a user cannot control

**What it is.** Some conditions are fixed for an ordinary user. The processor frequency policy raises a core's speed only after load appears on it. The system may move a process's memory pages between the two halves of the host on its own. No cores are reserved: any thread can be interrupted or moved to make room for another, and real-time priority is not available. Other people use the machine. The driver version (580) caps the CUDA version at 13.0. The kernel is Linux 5.15.

**What it makes possible.** These are the conditions any design has to work under. A design that depends on a quiet, pinned, fully warmed-up host will not always get one.

**How this was checked.** Read from `/sys` and `/proc` on this machine.

**Where to read more.** Linux kernel documentation: CPU frequency scaling, NUMA balancing, scheduler.

(card: `12-the-operating-system-what-a-user-cannot-control.md`)

### Ways to observe

**What it is.** Tools that work here without administrator rights: a per-kernel profiler with hardware counters, down to source lines and instructions (Nsight Compute); a timeline tracer for host and GPU activity (Nsight Systems); the framework's own profiler; a GPU debugger; sampling of GPU state (utilization, clocks, power, link speed, memory) through `nvidia-smi` or its library; and the Linux `perf` tool for a user's own processes. On this machine GPU hardware counters may be usable on the first GPU only.

**What it makes possible.** Anything that can be observed can be checked instead of assumed, including what the hardware does underneath the software.

**How this was checked.** The tools are installed and have been used on this machine.

**Where to read more.** Nsight Compute and Nsight Systems documentation; `man perf`; NVML reference.

(card: `13-ways-to-observe.md`)

### The framework underneath

**What it is.** The framework keeps its own pool of GPU memory and hands out pieces without asking the driver each time; the pool's behaviour can be tuned and inspected. New operations can be written in C++ or CUDA and loaded as extensions, built ahead of time or when the program starts. The framework exposes streams, events, pinned host memory and non-blocking copies. Each operation passes through a dispatch layer on the host before any GPU work is issued.

**What it makes possible.** The framework's defaults are one arrangement among several it supports, and anything it lacks can be added beside it.

**How this was checked.** From the installed framework (torch 2.14); not exercised here.

**Where to read more.** PyTorch documentation: CUDA semantics, memory management, C++ extensions.

(card: `10-the-framework-underneath.md`)
