# T2-1: spatial prefill/decode overlap (prefill lane on a green-context SM partition)

team: T2 (leader-2). Status: proposal. Champion reference: T1-042, 942.2 tok/s.

## Why this lever
- Today every prefill runs inside a mixed step that serializes it with one decode step. A mixed step takes ~94 ms, against 25.5 ms for a pure decode step (KB56). Its prefill part is tensor-bound: bf16 GEMMs at M=256-320 run at 125-140 TF, close to the 144-158 TF dense peak (measured, job 1).
  - Per trial, the marginal prefill time is ~400 x (94 - 25.5) ≈ 27 s of ~97 s.
  - During those ~94 ms, the 15 decoding requests advance only one step.
- The decode step is the opposite: memory- and latency-bound.
  - Marlin's 13.5 ms has a compute floor of only ~8 ms.
  - During the 6.2 ms of ARs per step, the SMs are mostly idle.
  - So the tensor cores sit idle for ~16 ms of every 25.5 ms decode step.
- Idea: an old one (NanoFlow, Bullet, semi-PD style intra-GPU spatial sharing) in a setting where it fits unusually well. The 4090 has a lopsided compute/bandwidth ratio and no P2P, so the AR windows are long.
  - Run new requests' prefills as a separate **prefill lane**: their own forward, on a green context of f SMs (torch.cuda.green_contexts, works on sm_89, job 1).
  - Run it concurrently with the ongoing decode steps, which stay on the plain stream with a Marlin grid sized 128-f.
  - A request joins the decode batch when its prefill (and first token + MTP drafts) completes.
  - Same math per request (batch composition changes only, as today): exact up to fp reordering.
- Not the same as chunked-prefill piggybacking, which r12 ruled down. Piggybacking adds rows to the same GEMMs at the compute margin, ~0.28 ms per token (KB46). The lane instead fills idle tensor time with concurrent kernels.

## Measured so far (seed: jobs 1, 4, 6; bank/T2-001; ~3.3 GPU-min)
- Green contexts partition linearly (gate_up 32/64/96 SMs -> 35.8/71.5/106.5 TF, job 1).
- Real FP8 Marlin, 16 layers x 4 GEMMs, CUDA graphs, GPU 0 (job 6):

  | f (prefill SMs) | decode chain M=48, co-run vs alone | prefill M=256 rate co-run |
  |---|---|---|
  | 0 | 3.99 ms | - |
  | 32 | 5.25 ms (x1.28 vs full GPU) | 32 TF |
  | 48 | 5.75 ms (x1.44 vs full; x1.31 vs its 128-f grid) | 45 TF |
  | 64 | 6.49 ms (x1.63 vs full) | 59 TF |

  Here decode runs on the plain stream with sms=128-f, and prefill on a green ctx with f SMs.
- Configurations that fail:
  - Decode inside a green ctx: 1.8-5x slower.
  - The default Marlin grid (sms=128) on a partition: +45% from 2 waves.
  - Plain streams with priorities: graph replays serialize completely.

  So the implementation needs: a Marlin `sms` argument, decode on the plain stream, prefill in a green ctx.

## Forecast (vs T1-042)
Model per trial: the decode-step count stays ~2650 (all steps become decode steps). Steps that run while the lane is busy pay a slowdown. The lane must finish 400 prefills within the trial.
| part | value | status |
|---|---|---|
| Decode Marlin slowdown while co-running, f=48 | x1.31 (+4.2 ms on 13.5) | measured (job 6, pure GEMM chain, 1 run) |
| Rest of the decode step while co-running (AR 6.2, GDN/attn/norms 3.5 ms) | +10-25% (+1.5 ms) | assumed (AR is PCIe-bound; small kernels lose SM slots and bandwidth) |
| => decode step while the lane is busy | ~31 ms (vs 25.5) | half measured |
| Prefill GEMM rate on the lane, f=48 | 45 TF -> 260-token prompt GEMMs (6.3 TF/rank) ≈ 140 ms | measured (job 6) |
| Prefill non-GEMM (GDN chunk, attention, lane ARs on copy engines) | ~25 ms per prompt on the lane | assumed (18.5 ms marginal on the full GPU, scaled) |
| => lane busy ~66 s/trial; T ≈ 2115 x 31 ms + 535 x 25.5 ms ≈ 80 s vs 96.8 s | | model |
- **Payoff if it works: +20% over T1-042 (~1130 tok/s).** The best f in the model is 48-56 (f=32 is lane-bound at +12%, f=64 gives +19%). More is possible if the lane also uses the AR windows (not credited) or f adapts to queue depth.
- **Central estimate: +7%. About 25-30% chance of the full payoff.** Main risks:
  1. in-server interference is worse than the GEMM-only bench (L2: the champion's evict_last prefetch during ARs, KB25; GDN state traffic; PCIe contention between lane ARs and decode ARs);
  2. engineering: vLLM V1 runs one batch at a time, so this needs a second set of runner buffers/metadata, a second AR instance, a thread-safe forward context, and an async lane in the scheduler (out-of-order batch completion);
  3. TTFT grows (prefill ~165 ms on the lane + queueing; the gate leaves room: 1100 -> ~1600 ms).
- It stacks with T3's draft head: better acceptance shortens decode, while the prefill time this lane hides stays the same.

## Roadmap (with kill gates)
1. **M1, in-server interference probe (~25 GPU-min).** Champion server plus a synthetic lane: in each TP worker, a side thread on a green ctx loops the real prefill GEMM chain (M=256, all 64 layers' shapes) plus copy-engine host traffic at the lane's AR volume. Bench c=16 vs off, ABBA. Measures the real decode-step slowdown (TPOT, step time) and the lane rate at f=32/48/64. Includes the 2-line Marlin sms patch.
   **Gate:** decode step slowdown ≤ ~25% at f=48 with lane ≥ 40 TF; else re-forecast or stop.
2. **M2, the prefill lane in the engine (~60 GPU-min of debug/bench).**
   - Scheduler: new requests go to an async lane batch; they join decode on completion (batch-queue style, out of order).
   - Worker: second runner state/buffers for the lane; lane forward on the green-ctx stream, eager or with its own prefill graphs (the decode runner then drops its prefill graphs, so graph memory is ~flat); separate host/DMA-AR instance; Marlin grid 128-f for decode graphs.
   - Unofficial same-job A/B vs T1-042, GSM8K-50, 128K test.
3. **M3, tune + official (~40 GPU-min).** Tune f, merge queued prefills into one lane batch, run the lane during idle decode, check the TTFT gate, official eval.
