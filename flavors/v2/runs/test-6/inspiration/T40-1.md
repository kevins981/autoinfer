# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Representation

**The principle.** The same information can be written in many forms. Forms differ in size, and in which operations are cheap on them. The cost of storing, moving and processing follows the form, not the information. A form is usually chosen once, for convenience, and everything afterwards pays for it.

**The waste.** Extra size and extra steps caused by the form, not by the information.

**General directions.**
- **A smaller form:** no larger than the information it holds.
- **A form that makes the frequent operation cheap:** even if rare operations get dearer.
- **Arrange for use:** put next to each other what is used together.
- **Convert once:** at the edge, not repeatedly inside.
- **Several forms:** the same information kept in different forms for different uses.

**Illustrations** (examples only; the best use of this principle may look like none of them). Arithmetic is easy in Arabic numerals and hard in Roman ones. A phone book is sorted by name because that is how it is searched. A map and a list of turns hold the same route for different uses.

(card: `13-representation.md`)

### Overqualified work

**The principle.** Expensive work is often applied to many candidates, of which only a few matter to the final answer. If a cheap test can tell which candidates cannot matter, the expensive work is needed only for the rest. The final answer still comes from the expensive, exact work, so it stays exact. The cheap test only has to avoid ruling out a candidate that matters.

**The waste.** Exact work spent on candidates that a cheaper test would have eliminated.

**General directions.**
- **Cheap pass first:** then exact work on the survivors only.
- **Use bounds:** a cheap bound can prove a candidate cannot win without evaluating it.
- **Stages of rising cost:** each stage removes candidates before the next, dearer one.
- **Order the tests:** cheapest and most selective first.

**Illustrations** (examples only; the best use of this principle may look like none of them). Security screens everyone quickly and searches a few by hand. An index rules out most rows before any is read. A chess program drops moves that a bound shows cannot beat the best found so far.

(card: `05-overqualified-work.md`)

### Repetition

**The principle.** Any piece of work is a function: it takes inputs and produces an output. The output contains nothing that wasn't already determined by the inputs. So work is only necessary when the inputs are new. If the inputs were seen before, the output already exists somewhere. If part of the inputs is new, only the part of the output that depends on it needs to be made.

This holds for computing a value, and equally for moving or storing one: sending something to a place that already has it is the same waste.

**The waste.** The work done, minus the work the new information required.

**General directions.**
- **Remember:** keep an output so the work isn't done again. This trades memory for work.
- **Share:** produce an output once and let everyone who needs it use the same copy.
- **Update by difference:** when the inputs change a little, compute only what the change affects.
- **Do it ahead:** if the inputs are known long before the output is needed, the work can be done once, early.

**Illustrations** (examples only; the best use of this principle may look like none of them). Incremental compilation rebuilds only what a change touched. Rsync sends only the parts of a file the other side lacks. A spreadsheet recomputes only the cells that depend on the edited one.

(card: `01-repetition.md`)

### Boundaries

**The principle.** Systems are divided into parts so that each can be built and understood on its own. Every boundary has two costs:
- **Crossing:** things are converted, copied, checked and handed over.
- **Blindness:** each part decides with only what it can see. It can't use what its neighbours know, so it must assume the worst.

**The waste.** The cost of crossing, plus the better decisions missed because knowledge stops at the boundary.

**General directions.**
- **Pass knowledge across:** tell the other side what you know, so it needn't assume or rediscover it.
- **Merge parts:** that work on the same thing.
- **Go around a layer:** when the service it provides isn't needed on this path.
- **Move the boundary:** to where fewer things cross it.

**Illustrations** (examples only; the best use of this principle may look like none of them). Two people who share a language need no interpreter. A form that passes through five departments waits at each desk. A compiler that sees across a function call can simplify both sides.

(card: `11-boundaries.md`)

### Excess guarantees

**The principle.** Every part of a system makes promises to whatever uses it: about order, exactness, freshness, completeness, timing. Each promise costs work to keep. Promises are usually set strong, because strong is safe and the users' real needs weren't known. Often what the users actually rely on is weaker.

The promises a system makes to the outside world are set by its requirements. The promises its parts make to each other are choices.

**The waste.** Work spent keeping a promise nobody relies on.

**General directions.**
- **Ask who relies on it:** for each promise, find what would break without it.
- **Weaken what nobody relies on:** while keeping everything the outside depends on.
- **Keep it only where it matters:** at the points or moments where it is relied on.
- **Keep it more cheaply:** the same promise, delivered by a different mechanism.

**Illustrations** (examples only; the best use of this principle may look like none of them). Not every letter needs registered mail. A bank need not post each payment the instant it is made. A list need not be fully sorted to find its largest entry.

(card: `18-excess-guarantees.md`)

## This machine: hardware

### Main memory and how fast it can be read

**What it is.** Each GPU has 24 GB of GDDR6X memory on a 384-bit bus clocked at 10,501 MHz. At 21 Gbit/s per pin that is a theoretical peak of 1,008 GB/s. There is no error correction. The memory is not shared between the two GPUs.

**What it makes possible.** The peak rate puts a floor under any step that must read a given number of bytes: bytes divided by rate. Comparing that floor with a step's measured time shows whether the step is limited by reading memory or by something else.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes). The peak rate is arithmetic from the bus width and data rate, not a measurement.

**Where to read more.** Ada Tuning Guide; the Nsight Compute memory metrics.

(card: `05-main-memory-and-how-fast-it-can-be-read.md`)

### Dividing one GPU into parts

**What it is.** Green contexts give a program several lightweight contexts on one GPU, each owning a fixed subset of the SMs. On this chip family a part is at least 4 SMs, in multiples of 2. Work in one part does not take SMs from another. The documentation notes that disjoint parts are not guaranteed to run at the same time.

**What it makes possible.** Different kinds of work can each get a known share of the chip instead of contending for all of it.

**How this was checked.** From the documentation; not tried on this machine.

**Where to read more.** CUDA Programming Guide: Green Contexts.

(card: `13-dividing-one-gpu-into-parts.md`)

### No direct path between the two GPUs

**What it is.** On this machine one GPU cannot read or write the other's memory (peer-to-peer access is reported as not supported), and there is no dedicated GPU-to-GPU link. Data going from one GPU to the other travels up one link into host memory and down the other link. Libraries that depend on direct access between GPUs do not apply here.

**What it makes possible.** Every exchange between the GPUs has two hops and passes through memory the host processors can also see. The host is on the path whether it takes part or not.

**How this was checked.** `nvidia-smi topo -p2p r` reports peer-to-peer as not supported.

**Where to read more.** CUDA Programming Guide: Programming Systems with Multiple GPUs.

(card: `21-no-direct-path-between-the-two-gpus.md`)

### Other engines, power and clocks

**What it is.** Besides compute, each GPU has video encoders (two), a video decoder, a JPEG engine and an optical-flow engine; all are idle in a compute program. The compute clock is not fixed: it ranges up to 3,105 MHz and moves with load, temperature and the power limit. The limit is set to 450 W per GPU, and an ordinary user cannot change it.

**What it makes possible.** The same code can run at different speeds at different moments, for reasons outside the code. The engines for video are separate hardware that compute work does not slow down.

**How this was checked.** Read from `nvidia-smi`.

**Where to read more.** `nvidia-smi -q`; NVIDIA Video Codec SDK documentation.

(card: `19-other-engines-power-and-clocks.md`)

### Graphics hardware a compute program can reach

**What it is.** The chip carries hardware built for graphics that compute code can also use. Texture units fetch from a 1-, 2- or 3-dimensional array and blend the neighbouring entries in hardware in a single fetch (the blend weights have limited precision), with built-in handling of out-of-range coordinates; arrays can be up to 131,072 wide in one dimension. The ray-tracing units search a hierarchy of bounding boxes in hardware; they are reached through a separate library.

**What it makes possible.** A table lookup with interpolation, or a search over spatial data, can be done by dedicated hardware that is otherwise idle in a compute program.

**How this was checked.** Texture limits queried from the device. The ray-tracing path was not checked on this machine.

**Where to read more.** CUDA Programming Guide: texture and surface memory; the OptiX documentation.

(card: `18-graphics-hardware-a-compute-program-can-reach.md`)

## This machine: software

### Parallel building blocks

**What it is.** A library of general parallel algorithms for the GPU is installed, in C++ and with a Python interface: sort, scan (running totals), reduce, select the items that meet a condition, partition, remove duplicates, histogram, run-length encode, search, merge.

**What it makes possible.** Problems that look inherently sequential, such as compacting a list or grouping equal items, have well-known parallel forms that are already written.

**How this was checked.** The package is installed (CCCL 13.3); not exercised here.

**Where to read more.** CCCL documentation (Thrust, CUB, `cuda.cccl`).

(card: `06-parallel-building-blocks.md`)

### How Python runs

**What it is.** The Python here is 3.12. One thread at a time executes Python code within an interpreter; the others wait for a lock. Native code called from Python can release the lock while it works, and most heavy library calls do. Separate processes each have their own lock, and so can separate interpreters within one process (in this version they can only be created from native code). Starting a thread is cheap and it shares all memory; a process is isolated and shares only what is arranged.

**What it makes possible.** Whether two pieces of host work truly overlap depends on where the lock is held, not on how many threads exist.

**How this was checked.** Version read from the environment. Whether a given library call releases the lock has to be checked case by case.

**Where to read more.** Python documentation: the global interpreter lock, `threading`, `multiprocessing`.

(card: `09-how-python-runs.md`)

### Compiling a whole sequence of operations as one

**What it is.** The framework can trace a model's sequence of operations and hand it to a compiler as one unit, which may fuse operations, drop intermediate results and generate code specialized to the shapes seen. Separately, a sequence of GPU operations can be captured once and replayed as a graph.

**What it makes possible.** Boundaries between operations are a choice of the code as written, not of the computation.

**How this was checked.** Part of the installed framework (torch 2.14); not exercised here.

**Where to read more.** PyTorch documentation: `torch.compile`, `torch.fx`, CUDA graphs.

(card: `04-compiling-a-whole-sequence-of-operations-as-one.md`)

### Sharing without copying

**What it is.** Several mechanisms let two parties use the same bytes. Host processes can share memory by name (63 GB available in the memory-backed file system). GPU memory can be shared between processes. Libraries in one process can hand each other GPU arrays without a copy through a standard exchange format (DLPack) or a common array interface. Message passing between processes is available with zero-copy for large messages.

**What it makes possible.** A boundary between processes or between libraries does not have to cost a copy.

**How this was checked.** The mechanisms are present in the installed software; not exercised here.

**Where to read more.** DLPack; PyTorch `torch.multiprocessing`; CUDA Programming Guide: Interprocess Communication; ZeroMQ guide.

(card: `08-sharing-without-copying.md`)

### Compiling while the program runs

**What it is.** GPU code does not have to be compiled before the program starts. A program can generate source, compile it in memory (NVRTC), link it with other compiled pieces while still optimizing across them (nvJitLink), and load the result, all while running. The Python kernel languages here work this way already.

**What it makes possible.** At run time the program knows things that were unknown beforehand: sizes, shapes, constants, which case actually occurs. Code compiled then can have them built in.

**How this was checked.** The libraries are installed (NVRTC 13.0, nvJitLink 13.4); not exercised here.

**Where to read more.** NVRTC and nvJitLink documentation; `cuda.core` documentation.

(card: `02-compiling-while-the-program-runs.md`)
