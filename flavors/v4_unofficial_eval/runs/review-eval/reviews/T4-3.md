## reviewer (05:32:12)

I agree with **“screen negative; don’t promote”**, with narrower causal claims. The bank diff matches the current workspace.

- **The +0.37 ms observation checks out.** Recomputing the first 2,717 iterations gives D=16 medians of 30.44 ms ON versus 30.07 ms OFF (1,621/1,622 samples). Those iterations share one server start per mode, so they don’t establish a repeatable regression. Throughput is +0.17%, also inconclusive.

- **The microbench supports no demonstrated fusion win.** Fused and unfused timings overlap at M=16/48; M=96 generally disfavors fusion. However, “AR transfer-bound” is stronger than the evidence: these timings show that **HMAR plus the prefetch join dominates**, without separating PCIe transfer, flag waits, synchronization, or prefetch costs.

- **The code supports chunk-level serialization, with a wording correction.** In [hmar.cu](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-arn/vllm/vllm/distributed/device_communicators/hmar/hmar.cu:184), each block publishes its whole chunk, waits, reads/sums the whole peer chunk, then starts normalization. Up to six rows share one block through sequential vector passes; it isn’t literally a row-by-row loop. This plausibly explains lost parallelism, but does not prove the measured slowdown’s cause. “Only per-row pipelining could win” and the 0.3–0.4 ms ceiling should be hypotheses/estimates.

- **Exactness is partial and sample-specific.** Logs substantiate bitwise AR sums, residuals and scales on the tested inputs, plus sparse small y differences and ~0.25–0.29% differing FP8 codes. They do **not** establish that every FP8 mismatch is a tie-rounding difference or ≤1 FP8 ULP. The probe changes reciprocal arithmetic too, and `maxdq_in_scale_units` divides FP8 code values by scale, so it isn’t a valid ULP bound. GSM8K-50 is only a smoke test; revival needs a proper numeric bound and GSM8K-250.
