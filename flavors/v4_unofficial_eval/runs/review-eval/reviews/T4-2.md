**Keep this as a screen negative, but revise the bottleneck conclusion. The code also needs a state-indexing fix before revival.**

1. **Correctness bug: `state_indices` can be strided.**  
   [recurrent_prefill.py:37](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-rp/vllm/vllm/model_executor/layers/mamba/gdn/recurrent_prefill.py:37) loads `state_idx_ptr + i_n`, assuming contiguous indices. Without spec rows, the builder supplies `block_table_tensor[:, 0]`, potentially with stride `1 + num_speculative_blocks`; slicing the prefill tail preserves that stride. For a table `[[3,4,5], [9,10,11]]`, the kernel uses `[3,4]` instead of `[3,9]`. Multiple prefills can therefore read or overwrite another slot. Pass `state_indices.stride(0)` into the kernel. The supplied numeric tests use one sequence and cannot detect this.

2. **Invalid-slot handling protects stores, but not loads.**  
   [recurrent_prefill.py:41](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-rp/vllm/vllm/model_executor/layers/mamba/gdn/recurrent_prefill.py:41) loads state whenever `has_init` is true, including `idx <= 0`. Slot zero is reserved; a negative index can read before the allocation. Zero-length padding returns safely before this, and fresh rows avoid the load. I did not establish a live, nonempty invalid-slot case in these logs, but the boundary contract needs fixing or explicitly enforcing before reuse.

3. **“The premise was an nsys artifact; mixed steps are mostly GPU-bound” is not established.**  
   The unprofiled results support smaller mixed-step latency and a useful small-prompt improvement. Recomputing matched shapes—one 58–64-token prompt plus 15 decoding requests—gives **54.2 ms ON versus 65.3 ms OFF**, across 20 and 18 observations.

   However, [`elapsed_ms` wraps a future wait](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-rp/vllm/vllm/v1/engine/core.py:827). That wait includes worker CPU launch delays as well as GPU execution. It cannot distinguish them. The ~52 ms floor is an estimate from a profiled T3-001 execution, whereas these benches use T3-003; subtracting it does not measure unprofiled CPU stalls. Substantial GPU work also does not establish which resource limits progress.

   The defensible conclusion is: **nsys likely exaggerates launch overhead; this replacement improves small mixed steps and loses on longer ones. The unprofiled bottleneck split remains unresolved.**

4. **The timing accounting does not establish a `<1%` ceiling for a lower threshold.**  
   I reproduced the [iteration table](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/bank/T4-001/eval/iter_quickbench/table.md). Total-token bins also differ from the dispatch condition, which uses maximum per-sequence length.
