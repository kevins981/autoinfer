# T3-2: confidence-budgeted MTP verification (fixed verify width, on-device slot selection)

team: T3 (leader-3). Pivot from T3-1, which is closed (T3-001..004). Champion reference: T1-042,
942.2 tok/s. Team balance at writing: 75.5 GPU-min (this pivot doesn't reset the grant).

## Idea
- Today every request verifies exactly k=2 drafts: M = 16 x 3 = 48 verify tokens per decode step.
- Instead: draft up to K_MAX = 3-4 steps, then verify only the batch's best B = 32 draft slots,
  ranked by survival probability, the running product of the draft head's own confidence. M stays
  at 48, the champion's graph size, so the target forward costs about the same. Confident
  requests get 3-4 slots, unconfident ones 0-1.
- Output is exact: verification is unchanged, only which draft tokens are verified changes.
- The slot selection runs on the GPU from the current step's confidences. That avoids the stale-
  confidence problem of a CPU-side budget, which removes most of the gain (T3-005 stale check).
- Prior art: vLLM's DSpark adaptive verification (`v1/worker/gpu/spec_decode/adaptive_verification.py`,
  gated to method=dspark: CPU budget from stale confidences, on-GPU ranking kernel). We would port
  the ranking kernel and the batch compaction to MTP on the champion stack.

## Evidence so far (T3-005, job t3-conf5, 0.3 GPU-min; agents/leader-3.w1/data/sim_all_output.txt)
- Offline per-position K=4 chains of the stock head on 142,889 positions of target-generated
  text (no training involved). Pooled cumulative acceptance 0.765 / 0.541 / 0.378 / 0.268.
  Fixed k=2 reproduces the in-server E: 2.316 vs 2.325.
- Calibration: confidence ranks acceptance well. 47% of step-1 drafts have confidence >= 0.95
  and are accepted 97.6% of the time. Mid bins are overconfident, but survival quintiles are
  monotone.
- Simulation, 20,000 batches of 16, current-step ranking, champion step-time model:

  | policy | E/request | ms/step | E/t vs k=2 |
  |---|---|---|---|
  | fixed k=2 (today) | 2.316 | 25.50 | 1.000 |
  | fixed k=3 | 2.699 | 30.53 | 0.973 (matches KB20's "k=3 doesn't pay") |
  | K_MAX=3, B=32 (M=48) | 2.510 | 26.05 | 1.061 |
  | K_MAX=4, B=32 (M=48) | 2.578 | 26.60 | 1.067 |
  | K_MAX=4, rule (d) | 2.735 | 28.15 | 1.070 |

  Step-time model: 25.5 ms at M=48, 0.28 ms per verify token (KB46), drafter 0.55 ms per draft step
  (KB26/KB41). Sensitivity range over slope 0.20-0.35 and drafter 0.4-0.8 ms: 1.053-1.093.
- Fixed B=32 doesn't change M, so its verify-side cost needs no slope assumption. Only the extra
  draft steps are assumed. The E gain at B=32 (+8.4% K_MAX=3, +11.3% K_MAX=4) is measured
  offline.

- **Payoff if it works: about +6% over T1-042** (K_MAX=4 with a better ranker and dynamic B, about
  1000 tok/s). Upside to +8% if the extra draft steps are cheaper than modeled or isotonic
  calibration helps (being measured now, offline).
- **Central estimate: +2.5%. About 30% chance of the full payoff.**
- Main risks:
  - The GDN spec-state memory at K_MAX > 2 (KB13: blocks per request scale with
    num_speculative_tokens; 13 blocks at k=3 fitted only 14 of 16 requests). T1's replay may make
    the per-token slots dead (upstream already sets them to 0 for ReplaySSM). This needs proof.
  - Varlen GDN replay kernels and the CUDA-graph integration on the champion's custom paths.
  - The drafter costing more than modeled.
- Kill criteria:
  - (1) The in-server drafter step costs > 0.9 ms (then K_MAX=3 nets < +3%).
  - (2) The GDN memory can't be freed without breaking the 128K test or 16-request admission.
  - (3) Prototype E/t on the unofficial bench < +3% same-job.
