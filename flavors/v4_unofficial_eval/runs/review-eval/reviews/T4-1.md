   - Selecting/scattering spec and non-spec rows.
   - Separate convolution paths.
   - Triton speculative recurrence for the existing decoding requests.
   - Prefill initial-state gather and masking.
   - The FLA chunk pipeline and final-state scatter.

   These operations belong explicitly in the graph and cost model. The gather/mask/chunk/scatter sequence is visible at [the prefill branch](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:2046). 4. **#2 is schedulable, but neither a 1600-token alignment barrier nor a smooth 96–160-row cost model is correct.**

   Prefix caching selects Mamba `align` mode and requires chunked prefill. Crucially, the scheduler explicitly allows **sub-block chunks when the block exceeds the configured chunk limit**, retaining private running state until a cacheable boundary. A budget below 1600 therefore does not inherently stall this model. It still clips at required block/checkpoint/shared-prefix boundaries. [Alignment logic](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/vllm/v1/core/sched/scheduler.py:564).

   The token budget covers the entire scheduled batch. With 15 decoding requests at k=2, approximately 45 rows are already consumed; a 96-token budget leaves approximately 51 for prompts, subject to alignment and scheduling order. Running requests are processed before new admissions, but an in-progress prefill can consume budget within that running list; this is not a guarantee that every existing decoder gets scheduled. See [running-request budgeting](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/vllm/v1/core/sched/scheduler.py:857).

   There is also a **transport discontinuity at 96 padded rows**:

   - HMAR accepts at most `96 × 5120 × 2` bytes.
   - Its path enables the champion’s L2 prefetch.
   - Larger inputs use NCCL and lose that prefetch.

   Thus 96 and 112/128/160 are materially different configurations. [HMAR eligibility and prefetch](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/vllm/distributed/device_communicators/host_mapped_all_reduce.py:189). Dense computation uses the graph-padded token count, not necessarily P+decode rows. [Runner padding](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/vllm/v1/worker/gpu/model_runner.py:1463).

   Smaller chunks also repeat convolution, GDN setup/state traffic, metadata and draft work many more times. Those costs survive a launch fix. Conversely, **fewer, larger prefill-bearing steps** deserve a priced row when fixed overhead dominates, with latency as the tradeoff. I would retain the small-budget experiment as a cheap conditional screen, but remove its status as the second-most-likely win.

The corresponding decode break-even p₃ is approximately **0.25**, not 0.33. Reprice the candidate after establishing capacity.

6. **#4 is valid in principle, but its state-copy contract is wider than the map implies.**

   The CUDA kernel reads slot `accepted−1` and writes each row’s state. The mixed Triton path follows the same convention. [CUDA source selection](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/csrc/gdn/fused_gdn_decode_kernel.cu:174).

   Prefix-cache migration is an additional correctness boundary:

   - Generic temporal copying selects `block_ids[cur_block_idx + accepted−1]`.
   - GPU pre-copy/post-copy use the equivalent temporal-slot offset.
   - Preprocessing can then reset the accepted count to one.

   [Temporal copy specification](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/vllm/model_executor/layers/mamba/mamba_utils.py:391), [GPU temporal copying](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/vllm/v1/worker/mamba_utils.py:352), [accepted-count reset](/scratch/kevinsong/learning/autoinfer/flavors/v4_unofficial_eval/runs/review-eval/workspaces/t4-champ/vllm/vllm/v1/worker/mamba_utils.py:529).

   A deferred state must be materialized before those copies or understood by replacement copy logic. Copying slot 1 after repurposing it for a log silently corrupts state. Test boundary crossing, cache reuse/branching, mixed batches, fresh requests and resumed requests—not just steady decode.

   Include replay arithmetic in the price: at acceptance 2.33, replay averages about **1.33 previous rows per step**. “Same fp32 arithmetic” alone does not establish bitwise replay; normalization, decay calculation, reduction order and FMA behavior must also match. Suppressing destination writes is a useful upper-bound microbenchmark only if source selection stays valid; it excludes replay cost.

   Finally, retaining slot 1 as log storage does **not** itself reclaim the state-slot capacity that k=3 needs. Allocation changes are a separate optimization.

I would retain the existing pruning of stock DBO and the tested HMAR pipeline implementations as engineering/budget decisions. Two broader exclusions should be softened:

- **Reduced vocabulary:** T1-002 rejects one 32K tokenizer-prefix subset, not all larger subsets, generic-corpus subsets or FP8 subset heads. Mark the family low priority, not established negative.
- **Draft/verify overlap:** simultaneous HBM-heavy kernels have little opportunity, but drafting during another cohort’s collective window is not ruled out by that argument. It needs a separate schedule and contention estimate.

My revised order is **specific mixed-path launch/fusion work; DeltaLog feasibility; memory-feasible k=3; then small-budget prefill conditional on measured costs**. The largest correction is to distinguish observed trace overhead from removable official-benchmark time before attaching +7–15% forecasts.
