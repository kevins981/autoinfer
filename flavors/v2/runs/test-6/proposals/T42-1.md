# T42-1: certified greedy decisions. The target lm_head is computed exactly only where the argmax can still be

Team T42 (research), leader-42. Evidence: bank/T42-001 (CPU only, 0 GPU-min so far). Sparring: sparring/ T42-1.

## The idea
Greedy speculative verification never uses the target's logits. It uses one discrete fact per row: which
vocab id is the argmax. Today each GPU streams its whole 124K x 5120 lm_head half for every decode step
(0.993 GB after T1-037's lossless code, 1.07 ms at M=64, ~95% of the read roof). That is about 4% of the
26 ms step, spent producing 248K numbers per row when the consumer reads one index.

The proposal is to certify the argmax and skip the rest:
1. **Screen.** Keep a b-bit integer plane of the lm_head: q = round(w/s), with a scale s per group of G
   weights along K. Every GPU streams the plane (0.38-0.44 of bf16 bytes) and computes approx_v = h.(s q_v).
2. **Bound, rigorously.** Hoelder per group: |h.w_v - approx_v| <= sum_g ||h_g||_1 s_g/2. The slack is also
   inflated by fp32 error bounds: the screen's own error (~ gamma_K * 2 qmax * slack, ~+4%), the error of the
   kernel that computes the reference logits, and half a bf16 ulp for logit rounding and ties. These are cheap
   per-row and per-group quantities.
3. **Rescore exactly.** Only ids v with approx_v + slack_v >= max_u(approx_u - slack_u) - eps can be the
   argmax. Their exact bf16 logits are computed with the full kernel's arithmetic, and the baseline tie-break
   picks among them. The decision is the baseline's by construction, not by statistics.

## What we already know (bank/T42-001, CPU, real lm_head, held-out final-norm hidden states)
- **Low rank is useless here.** The hidden states are nearly isotropic: r=512 captures 67% of the energy and
  r=1024 79%. Low-rank screening with a Cauchy-Schwarz bound keeps all 248,320 ids for every row, in all 12
  configs tried. This also explains why T27's PCA screen can only be approximate, which is fine for drafts.
- **Precision redundancy is large.** With an integer plane, the reference argmax was in the candidate set
  in 100% of rows:
  - b=7, G=128 (0.89 B/w): mean 4.0 candidates per row, max 51.
  - b=7, G=512 (0.88 B/w): mean 5.2, max 76.
  - b=6, G=128 (0.77 B/w): mean 24, max 769.
  - b<=5 fails: thousands of candidates.
  The top1-top2 logit gap has median 3.2 and p10 0.42. A 6-7-bit plane bounds the error well below that;
  truncation does not.
- **What is novel.** It is new to this run: KB52 closed the lm_head as "no longer a lever" on the basis of
  lossless codes, and T27's screen is approximate and drafter-only. As far as I know, exact certified
  argmax via quantized planes is not used for LLM greedy or speculative verification. Exact maximum
  inner-product search with bounds exists in recommender systems (LEMP, FEXIPRO), but with the low-rank/SVD
  bounds that this data refutes.

## What it could teach future teams
- **Decision-only consumers have a precision floor far below the data's.** The argmax of a 5120-dim bf16
  product is fixed by ~6-7 bits per weight. A tree or deeper-speculation team can then treat the
  lm_head's cost as nearly independent of rows: one plane pass plus a few dozen gathered rows per row.
- **Where the gain hides is not obvious.** Truncation (low rank) fails completely, while quantization
  (all coordinates kept, small bounded error) works. My own napkin math, and the spar's first challenge,
  predicted the opposite. That is worth a KB entry whatever the speedup.
- **HBM can be freed.** With b=7 the plane is 0.55 GB/GPU. If rescoring fetches the few exact rows
  (64 rows x ~4-24 candidates x 10 KB, under 16 MB/step across both ranks) from pinned host memory instead
  of keeping the bf16 copy on the GPU, ~0.45 GB/GPU of HBM comes back. The run has been capacity-bound
  before (KB13, KB16). What that capacity buys is not established yet.

## Forecast (honest)
- lm_head 1.07 ms -> ~0.55-0.65 ms including bounds, compaction and rescoring: about -0.45 ms/step.
- That is ~+1.7% decode and **~+1.0-1.3% e2e**, comparable to T27-002's +1.1%. The odds the kernel lands
  under 0.65 ms at M=64 are ~60%. The odds of 0 decision mismatches given a correct enclosure are ~95%;
  the risk is implementation, not math.
- Risks:
  - The GPU screen may be ALU-heavy: it does per-group scale and |h| sums for 64 rows. The plane must also
    stream at the roof, as T1-037's decoder does.
  - Tail rows: max 769 candidates at b=6, so b=7 is safer.
  - Memory, if the bf16 copy stays on the GPU next to the plane (+0.55 GB/GPU). The host-backed rescoring
    variant avoids this but adds a PCIe round trip (~2.5 us + ~8 MB/rank at ~22 GB/s ≈ 0.35 ms worst case;
    it must be measured).

## Plan and GPU need
- **Stage 1 (~6-8 GPU-min, inside the 20-min seed): kernel and enclosure.** A worker builds a standalone CUDA
  path for M=64 on one GPU: plane GEMV/GEMM + slack, then candidate compaction, then exact rescoring
  (on-GPU bf16 rows, plus a host-pinned variant).
  - Measure it in the same job as the champion's lmh_codec kernel at M=64. Use real hidden states (T3's
    dumps, >=100K rows, thinking on/off) and random adversarial rows.
  - Check decisions against the full kernel's bf16 argmax, bitwise, ties included.
  - The written enclosure proof goes in the record.
  - **Go:** full path <= 0.65 ms on GPU0 (the slow-clock GPU), 0 mismatches. **Kill:** > 0.8 ms or any
    mismatch that the enclosure doesn't explain.
- **Stage 2 (~25 GPU-min): in-server on T37-002.**
  - Plug into the local-argmax verify path on both ranks and choose the memory variant from stage 1.
  - Run GSM8K-50 as a smoke test (the decision is exact by construction).
  - ABBA vs T37-002 with all planned starts, and the 128K test if memory changes. Official eval only if
    every B beats every A.
- **Total ~30-35 GPU-min.** Stage 1 fits in the seed. I would ask for ~25 more only after stage 1 passes.

## Validity (for the manager's review)
The output is exactly the baseline's greedy decision: a rigorous bound plus exact rescoring. There is no
approximation of the model and no benchmark-specific data. The plane is derived from the checkpoint's own
lm_head at load, like T1-037's code. Open question for the manager: is a b-bit plane kept next to the
bf16 lm_head acceptable under "no copies that change the memory picture unfairly"? It is lower precision,
used only to screen, +0.55 GB/GPU. The host-backed variant would instead *free* HBM.
