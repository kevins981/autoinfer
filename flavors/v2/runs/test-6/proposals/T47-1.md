# T47-1 (research, leader-47): asymmetric waves. Use the decode pass as cover for the prefill's all-reduce

Team T47 (research), leader-47. GPU used so far: 0 of the 20-min seed. Evidence: CPU analysis of existing traces
(agents/leader-47/ana/, on agents/leader-42.w1/out/s2b/A = champion T37-002 node trace) and run records cited below.
Sparring: sparring/ T47-1 (3 turns).

## The observation
A prefill event is today one *joined* mixed step: 60 decode rows plus P prompt rows go through every GEMM and every
all-reduce together. Measured cost: decode pass 23 ms + 15 ms per event + 0.166 ms per prompt token (KB111). That is
about 23 s of an 80 s trial (29%), and is the largest gap to speed of light (SPEED_OF_LIGHT.md: ~8-16 s).

Two things are serialized in that step that don't have to be:
- **The prompt rows' all-reduce is exposed.** AR-off floor 0.109 vs 0.160 ms per prompt token (T30-001). During it no
  kernel runs (copy-only time 42.6 of 141.8 ms at pt 401-1000, T30-002).
- **The decode rows ride along and pay the prefill's price.** Once prompt rows push M past 64, every decode row pays
  compute-bound GEMM cost (KB118 step: 0.07 -> 0.16 ms/row). Their own all-reduces are serialized as well.

## The idea
Split the mixed step into two **asymmetric** waves that are independent through all 64 layers (different requests):
- **wave D:** the 16 decode requests' rows. This is exactly a decode pass, already a FULL CUDA graph: one launch on a
  high-priority side stream, no host cost.
- **wave P:** the prompt rows, compute-bound, on the main stream with its copy-engine all-reduce.

The two waves are complementary. While P waits on its copy-engine AR (no SMs, x1.0-1.1 coexistence with HBM traffic,
T8-001), D's memory-bound GEMMs run. While D waits on its AR, P's compute runs.

The joins happen only at the end: lm_head/sampling, and the drafter.

### Why it is new relative to the run
- **T30 (two waves):** split rows *symmetrically*, so each wave had only one ~0.1-0.2 ms GEMM of cover per
  0.3-0.5 ms AR. That gave -11% at best, and in-server it was host-bound (eager waves).
  - Here the cover wave is a whole decode pass: ~19 ms of GPU work, memory-bound, graph-launched.
  - The covered wave is the prefill: long ARs, compute-bound GEMMs.
  - The resource profiles differ (DRAM vs tensor/PCIe), which is what T30's waves lacked.
- **T2 (spatial prefill lane):** partitioned SMs between two compute streams, which is zero-sum (KB59).
  - Here nothing is partitioned. The gain is only the communication gaps that today hold no kernel.
- **Field:** NanoFlow-style intra-device overlap splits a batch into symmetric nano-batches on NVLink machines.
  - Splitting by *phase* specifically to cover PCIe-host-staged TP communication, with the decode graph as the cover,
    is new as far as I know.
- **The price is explicit.** D re-streams the weights (~13.5 ms of DRAM time, KB79/KB111). This pays only when that
  stream lands in gaps that are idle today. So there is a predicted crossover prompt length below which joined is
  better. That is a testable rule, not just a speedup.

## Napkin model (to be checked, not measured)
- Joined: T_J = 23 + 15 + 0.166 P.
- Split: T_S ~ P_chain + max(0, D_gpu - gaps), where:
  - P_chain = prefill-only step ~ 17.6 + 0.160 P (17.6 from a 64-token prefill-only step: 27.8 ms busy, traced, s2b/A
    steps.csv);
  - gaps ~ 0.051 P (exposed AR);
  - D_gpu ~ 19 ms (decode pass minus its exposed AR).
- Results:
  - P=260: T_J 81, T_S ~65 (-16 ms).
  - P=64: T_J 48.6, T_S ~44 (-5 ms).
  - Crossover near P ~ 30-40.
- Over 400 events, an upper bound of ~4-6 s/trial (+5-7%) with no interference. Concurrent kernels are zero-sum
  where they overlap (KB59), so I forecast **central +2-3%, payoff if it works +5-6%, odds of >= +2% ~35%**.
- The number that is useful for future teams, whatever the outcome: **how much of a prefill's exposed communication
  a memory-bound wave can fill on this machine**, measured at several prompt lengths. It sets the value of every
  "overlap prefill with something" design.

2. **Stage 2 (~25 GPU-min requested at resync, only if stage 1 passes).**
   - In-server: in the V2 runner, mixed steps with P >= crossover run the decode rows through the captured decode
     graph on a side stream, and the prompt rows through the existing prefill path. Join before sampling.
   - Same-job ABBA vs T37-002, FP8 GSM8K A/B not needed (no precision change), 128K gate.

## Risks (honest)
- **Concurrency may not materialize.** P's copy-engine AR is driven by flags polled from the main stream. If P's
  kernels occupy all SMs (255 regs x 256 thr, KB33), D's kernels wait for them, and vice versa. Stream priority helps
  only at block boundaries.
- **D's hostar uses SMs to reach the host.** Beside P's compute-bound GEMMs that may be slow (T4: hostar x2 beside a
  memory-bound GEMM). D could use its existing graph unchanged and accept that.
- **Memory.** A second set of activations/workspaces for wave D. The decode graph's buffers already exist, so this
  is likely small, but unmeasured.
- **The drafter and GDN state.** Wave D is the normal decode-graph path. The P request's first MTP step is
  unchanged.
