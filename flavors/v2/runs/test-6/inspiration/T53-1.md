# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Predictability

**The principle.** Waiting for a result is necessary only if the result can't be predicted. If a guess is usually right, and checking a guess costs less than waiting for the answer, work can go ahead on the guess and be corrected in the rare cases it was wrong. The gain is roughly (chance of being right x time saved) - (chance of being wrong x work wasted). It needs three things: a cheap guess, a cheap check, and a way to undo.

**The waste.** Time spent waiting for an answer that was largely known in advance.

**General directions.**
- **Guess and verify:** proceed on the likely answer; check it when the real one arrives.
- **Prepare ahead:** get ready what is likely to be needed next.
- **Follow several possibilities:** and keep the one that turns out right.
- **Improve the odds or lower the price:** a better guess, a cheaper check, or a cheaper undo.

**Illustrations** (examples only; the best use of this principle may look like none of them). A processor guesses which way a branch will go and runs ahead. A waiter starts a regular's usual order when they walk in. A disk reads the next blocks before they are asked for.

(card: `08-predictability.md`)

### Boundaries

**The principle.** Systems are divided into parts so that each can be built and understood on its own. Every boundary has two costs:
- **Crossing:** things are converted, copied, checked and handed over.
- **Blindness:** each part decides with only what it can see. It can't use what its neighbours know, so it must assume the worst.

**The waste.** The cost of crossing, plus the better decisions missed because knowledge stops at the boundary.

**General directions.**
- **Pass knowledge across:** tell the other side what you know, so it needn't assume or rediscover it.
- **Merge parts:** that work on the same thing.
- **Go around a layer:** when the service it provides isn't needed on this path.
- **Move the boundary:** to where fewer things cross it.

**Illustrations** (examples only; the best use of this principle may look like none of them). Two people who share a language need no interpreter. A form that passes through five departments waits at each desk. A compiler that sees across a function call can simplify both sides.

(card: `11-boundaries.md`)

### Excess guarantees

**The principle.** Every part of a system makes promises to whatever uses it: about order, exactness, freshness, completeness, timing. Each promise costs work to keep. Promises are usually set strong, because strong is safe and the users' real needs weren't known. Often what the users actually rely on is weaker.

The promises a system makes to the outside world are set by its requirements. The promises its parts make to each other are choices.

**The waste.** Work spent keeping a promise nobody relies on.

**General directions.**
- **Ask who relies on it:** for each promise, find what would break without it.
- **Weaken what nobody relies on:** while keeping everything the outside depends on.
- **Keep it only where it matters:** at the points or moments where it is relied on.
- **Keep it more cheaply:** the same promise, delivered by a different mechanism.

**Illustrations** (examples only; the best use of this principle may look like none of them). Not every letter needs registered mail. A bank need not post each payment the instant it is made. A list need not be fully sorted to find its largest entry.

(card: `18-excess-guarantees.md`)

### Rework

**The principle.** Some work is done and then thrown away: an attempt fails, a guess is wrong, a result arrives too late or is made invalid, something is retried from the start. Its cost was paid and it contributed nothing. This is often accepted as rare, and rarely measured.

**The waste.** All work whose result is discarded.

**General directions.**
- **Measure it:** how much work is thrown away, and why?
- **Detect the failure earlier:** before more work is built on top of it.
- **Keep what is still valid:** discard only the part that was wrong.
- **Fail less often:** remove the cause of the discarded attempts.
- **Make a failed attempt cheaper:** so that being wrong costs little.

**Illustrations** (examples only; the best use of this principle may look like none of them). A carpenter measures twice and cuts once. A long calculation saves its progress so a failure doesn't restart it. A factory inspects at each station, not only at the end of the line.

(card: `19-rework.md`)

### Repetition

**The principle.** Any piece of work is a function: it takes inputs and produces an output. The output contains nothing that wasn't already determined by the inputs. So work is only necessary when the inputs are new. If the inputs were seen before, the output already exists somewhere. If part of the inputs is new, only the part of the output that depends on it needs to be made.

This holds for computing a value, and equally for moving or storing one: sending something to a place that already has it is the same waste.

**The waste.** The work done, minus the work the new information required.

**General directions.**
- **Remember:** keep an output so the work isn't done again. This trades memory for work.
- **Share:** produce an output once and let everyone who needs it use the same copy.
- **Update by difference:** when the inputs change a little, compute only what the change affects.
- **Do it ahead:** if the inputs are known long before the output is needed, the work can be done once, early.

**Illustrations** (examples only; the best use of this principle may look like none of them). Incremental compilation rebuilds only what a change touched. Rsync sends only the parts of a file the other side lacks. A spreadsheet recomputes only the cells that depend on the edited one.

(card: `01-repetition.md`)

## This machine: hardware

### Every transfer has a fixed cost

**What it is.** Moving data across a link costs a fixed amount of time that does not depend on the size: a call into the driver, setting up the transfer, and learning that it has finished. Only above some size does the time grow with the number of bytes.

**What it makes possible.** For small transfers the count matters more than the bytes. The size at which the fixed part stops dominating can be measured, and it tells you which regime a given exchange is in.

**How this was checked.** A general property of this kind of link; the fixed cost on this machine is not stated here. Measure it.

**Where to read more.** CUDA Programming Guide: Asynchronous Execution.

(card: `23-every-transfer-has-a-fixed-cost.md`)

### More than one kernel at a time

**What it is.** A GPU can have up to 128 kernels resident at once. Kernels issued on different streams of one process may run at the same time when the first leaves SMs, registers or scratch memory free; otherwise they run one after another. Streams can be given priorities. The two GPUs are fully independent of each other.

**What it makes possible.** A small kernel does not have to wait behind a large one, and a kernel that cannot use the whole chip need not leave the rest idle.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Asynchronous Execution.

(card: `12-more-than-one-kernel-at-a-time.md`)

### Memory and signals shared between processes

**What it is.** GPU memory allocated in one process can be opened in another, which then reads and writes the same bytes without a copy. Events can be shared the same way, so one process can wait for work another process started. Memory pools give allocation and release that are ordered with the work on a stream, and a pool can be created so that its memory is exportable.

**What it makes possible.** Work on one GPU can be split across processes without paying for copies between them.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Interprocess Communication; Stream-Ordered Memory Allocator.

(card: `11-memory-and-signals-shared-between-processes.md`)

### What this chip does not have

**What it is.** Several features of newer NVIDIA chips are absent on this one: thread-block clusters and scratch memory shared across SMs; the bulk copy unit (TMA) that loads whole tiles with one instruction; moving registers between warps while a kernel runs; add, subtract and multiply directly on bfloat16 values (fused multiply-add on bfloat16 does exist); the block-scaled and 4-bit float formats. Scratch memory per SM is 100 KB, less than on the older data-center chip of the same family (164 KB) and the newer one (228 KB).

**What it makes possible.** Code written for newer chips often assumes these features. Here the same job has to be done another way, or the code falls back to a slower path without saying so. Knowing what is missing tells you which published designs carry over unchanged and which need rethinking.

**How this was checked.** The compiler rejects cluster launch for this chip; the assembler rejects the bulk copy, register reallocation and bfloat16 add; the device reports no cluster launch and no tensor-map access.

**Where to read more.** CUDA Programming Guide: Compute Capabilities; PTX ISA reference (the target notes under each instruction).

(card: `03-what-this-chip-does-not-have.md`)

### Telling the cache what to keep

**What it is.** A program can influence the second-level cache instead of leaving it to the default policy. Up to 49.5 MiB can be set aside for data marked to persist. A window of memory (up to 128 MiB) is marked per stream or per graph node, with a ratio that says what fraction of accesses in it get the persisting treatment; accesses can also be marked as streaming (use once, evict first). At the instruction level, a load or store can carry an eviction hint (evict first, evict last, do not cache), and there are instructions to prefetch into the cache, to change the priority of a range, and to discard a range without writing it back.

**What it makes possible.** The program knows which data it will need again and which it will not; the default policy does not. These controls let it pass that knowledge on.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes). The hint instructions were assembled for this chip; not run. The set-aside cannot be changed while the multi-process service is in use.

**Where to read more.** CUDA Programming Guide: L2 Cache Control; PTX ISA reference: `prefetch`, `createpolicy`, `applypriority`, `discard`.

(card: `07-telling-the-cache-what-to-keep.md`)

## This machine: software

### Sharing without copying

**What it is.** Several mechanisms let two parties use the same bytes. Host processes can share memory by name (63 GB available in the memory-backed file system). GPU memory can be shared between processes. Libraries in one process can hand each other GPU arrays without a copy through a standard exchange format (DLPack) or a common array interface. Message passing between processes is available with zero-copy for large messages.

**What it makes possible.** A boundary between processes or between libraries does not have to cost a copy.

**How this was checked.** The mechanisms are present in the installed software; not exercised here.

**Where to read more.** DLPack; PyTorch `torch.multiprocessing`; CUDA Programming Guide: Interprocess Communication; ZeroMQ guide.

(card: `08-sharing-without-copying.md`)

### The operating system: what a user cannot control

**What it is.** Some conditions are fixed for an ordinary user. The processor frequency policy raises a core's speed only after load appears on it. The system may move a process's memory pages between the two halves of the host on its own. No cores are reserved: any thread can be interrupted or moved to make room for another, and real-time priority is not available. Other people use the machine. The driver version (580) caps the CUDA version at 13.0. The kernel is Linux 5.15.

**What it makes possible.** These are the conditions any design has to work under. A design that depends on a quiet, pinned, fully warmed-up host will not always get one.

**How this was checked.** Read from `/sys` and `/proc` on this machine.

**Where to read more.** Linux kernel documentation: CPU frequency scaling, NUMA balancing, scheduler.

(card: `12-the-operating-system-what-a-user-cannot-control.md`)

### The framework underneath

**What it is.** The framework keeps its own pool of GPU memory and hands out pieces without asking the driver each time; the pool's behaviour can be tuned and inspected. New operations can be written in C++ or CUDA and loaded as extensions, built ahead of time or when the program starts. The framework exposes streams, events, pinned host memory and non-blocking copies. Each operation passes through a dispatch layer on the host before any GPU work is issued.

**What it makes possible.** The framework's defaults are one arrangement among several it supports, and anything it lacks can be added beside it.

**How this was checked.** From the installed framework (torch 2.14); not exercised here.

**Where to read more.** PyTorch documentation: CUDA semantics, memory management, C++ extensions.

(card: `10-the-framework-underneath.md`)

### Down to the instructions

**What it is.** The compiler's intermediate language (PTX) can be read, written by hand, and placed inline inside C++ code. The assembler reports registers used and spilled per kernel. The final machine instructions can be disassembled from any compiled kernel, including ones from libraries. The profiler can attribute time to single source lines and instructions.

**What it makes possible.** What a kernel really does is visible, and what the higher-level languages do not expose can still be written.

**How this was checked.** The tools are installed (`ptxas`, `nvdisasm`, `cuobjdump`) and the assembler was used to check the hardware cards.

**Where to read more.** PTX ISA reference; CUDA binary utilities documentation.

(card: `03-down-to-the-instructions.md`)

### How Python runs

**What it is.** The Python here is 3.12. One thread at a time executes Python code within an interpreter; the others wait for a lock. Native code called from Python can release the lock while it works, and most heavy library calls do. Separate processes each have their own lock, and so can separate interpreters within one process (in this version they can only be created from native code). Starting a thread is cheap and it shares all memory; a process is isolated and shares only what is arranged.

**What it makes possible.** Whether two pieces of host work truly overlap depends on where the lock is held, not on how many threads exist.

**How this was checked.** Version read from the environment. Whether a given library call releases the lock has to be checked case by case.

**Where to read more.** Python documentation: the global interpreter lock, `threading`, `multiprocessing`.

(card: `09-how-python-runs.md`)
