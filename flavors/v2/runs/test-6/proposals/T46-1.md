# T46-1 (research, leader-46): the host as a memory tier. PCIe is idle ~75% of a decode pass; can it add weight bandwidth and GPU memory?

Team T46, leader-46. GPU used so far: 0 (seed 20). Sparring: sparring/T46-1 (5 turns).

## Observation (from records, CPU only)
- A decode pass is ~26.2 ms. ~12.4 ms of it is streaming ~12.2 GB of weights per GPU at the HBM roof (KB47, KB111).
  Both GPUs' PCIe links carry traffic only during the 128 all-reduces, ~6 ms of the pass (KB109: ~45 us each).
  For the other ~20 ms, each link (~22-25 GB/s per direction) is idle.
- Memory, not bytes, is what has blocked several ideas: the 1.5x-weights PP/TP hybrid (T38), T42's screening plane
  (+0.6 GiB has OOMed, KB111), a replicated drafter, larger prefill graph grids (KB44 OOM).
- The bf16 embedding table is vocab-parallel: 1.27 GB per GPU, of which 64 rows (640 KB) are used per pass, and it
  costs an all-reduce per target pass and one per draft level (the "embed AR" in KB71's 4 drafter collectives).

## The idea
Treat pinned host memory as a third memory tier that both GPUs reach, and the idle link time as extra bandwidth:
1. **Embedding on the host (exact).** One full bf16 table in pinned host memory; each GPU gathers the rows it needs
   (zero-copy, ~30 us per 64 rows). Frees ~1.27 GB per GPU and removes 1 all-reduce per target pass and 1 per draft
   level (4 per step at k=3). Same values, so bitwise exact.
2. **Weights from the link (exact; the novel part).** Keep a small fraction f of each decode GEMM's FP8 weights in host
   memory and feed them during the GEMM phases while HBM streams the rest. Two feeds to test:
   - (a) SM zero-copy loads of the host slice (risk: KB66 saw SM host traffic slow x1.45 beside HBM-saturating kernels);
   - (b) a copy-engine ring: host -> a ~8-16 MB device staging ring that the GEMM consumes while the lines are still in
     L2. If dirty ring lines are overwritten before eviction, the slice crosses into the SMs without costing DRAM
     bandwidth: a PCIe -> L2 channel beside HBM. I haven't seen this measured anywhere in the run.
   Ceiling: 22-25 GB/s on ~980 GB/s is ~+2.5% weight bandwidth, ~0.3-0.35 ms per pass (~1.2% e2e). It also frees
   f x 12.2 GB of HBM (f=2.5% is ~0.3 GB per GPU).

## Why it's novel / what it teaches
The run treats each GPU as a closed box with ~980 GB/s and 24 GB, and the link as a communication cost only. If (2b)
works, the link becomes a bandwidth and capacity resource, and memory-blocked designs get a budget: 1.3-1.6 GB per GPU
at ~no throughput cost. If it fails, we learn why: whether DMA into L2 avoids DRAM, and whether a host feed beside
HBM is additive or zero-sum. KB59/62/70 found zero-sum for compute-plus-communication; this tests the bandwidth version.

## Honest forecast
- Direct speedup is small: embed AR removal ~0.15-0.25 ms/step, weight feed <= ~0.35 ms/step: **~+1-2% e2e at best**;
  ~50% odds that (2) is zero-sum, like the earlier overlap results.
- The value is the enabler (memory) and the answer to "is the link additive bandwidth".
