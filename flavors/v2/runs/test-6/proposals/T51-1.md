# T51-1 (exploit-long, leader-51): piggyback prefill in a captured mixed pass

## Idea
Prefill costs ~28% of the trial: each new prompt gets its own mixed step, costing ~15 ms fixed plus 0.166 ms per prompt
token (KB111). A 64-row decode pass is byte-bound: the FP8 MMA time at M=128 is ~86% of the weight-stream time.
So 96-192 prompt rows can ride in every decode pass and pay mainly their all-reduce (~0.07 ms/row), not their GEMM.
This is T37's original idea and T45-1's bet, re-priced. T45 killed it with a simulator that only looked at <=64-96 prompt
rows per pass. Its own cost model gives +7.4% / +9.9% at 96 / 128 rows (local_kb/leader-51.md).

## What the seed measured (bank/T51-001; jobs 432, 434; 8 GPU-min)
- Budget 192: -1.9%. Budget 160: -10.2% vs 2048 (one start each).
- Every pass that carries prompt rows costs ~51 ms of wall time, flat from 1 to 144 rows, against 24.9 ms for a decode
  pass. Total time tracks the number of mixed passes.
- GPU-side excess at ~100 prompt rows (nsys):
  - GEMM: +9.5 ms. All GEMMs leave t31b for bs_gemm and lose the AR-window prefetch.
  - All-reduce: +7 ms, ~0.07 ms/row.
  - Glue: ~5 ms (GDN prefill core 2, quant/attention/norm/other 3).
  - The ~51 ms wall floor is above the GPU span (42-48 ms). Host enqueue of the eager/piecewise mixed path is likely
    (KB89) but not proven.
- Calibrated sim (agents/leader-51/sim/pig2.py): reproduces the measured losses (-3.8 / -11.7 vs -1.9 / -10.2).
- Interpretation: this rejects today's mixed-pass implementation, not the direction.

## Roadmap and GPU
1. **M1, GEMM band (~8 GPU-min, microbench).**
   - T45's 64-layer chain with AR prefetch stand-ins, at M = 64 + {64, 96, 128, 144}.
   - Kernels: best existing configs per TP shape (t31b, bs_gemm, split-K variants from T38).
   - Gate: in-chain band <= 0.05 ms/row.
2. **M2, captured mixed pass (~20 GPU-min).**
   - Fixed buckets (64 decode + P prompt rows) as full CUDA graphs, with the GDN prefill core captured (T32_GDN_CAP
     asset) and the decode AR+prefetch path kept.
   - In-server step-log sweep. Gate: mixed pass <= 24.9 + 0.07P + ~8 ms, with the host floor gone.
3. **M3, GEMM band tuning in server (~20 GPU-min).**
   - Dispatch/config for M=96-208, and/or extending t31 past 96.
4. **M4, scheduler policy (B, chunking), same-job ABBA vs champion, GSM8K-250, 128K gate, official eval
   (~30 GPU-min).**

Total ~80 GPU-min (12 left from the seed). Exactness: chunked prefill and kernel dispatch are fp reorderings of the same
W8A8 math; GSM8K A/B and 128K gates are rerun at M4.

## Update after M1 (bank/T51-002, jobs 436/437, 2.8 GPU-min): gate FAILED on existing kernels
- Measured in-chain GEMM band: 0.069-0.072 ms/row at M=192, 0.09 at M=160 (gate 0.05). These are steps at m-tile
  boundaries, not a slope. Config and split-K tuning buy <=3%. A dispatch change cannot pass the gate.
- Cause: the existing kernels reach 1.36x the floor at M=128 and 1.70x at M=192 on TP shapes. The same bs_gemm on
  full-width shapes reaches 1.07-1.10x at M=128 (T38). Likely tiling/occupancy on half-width N, not physics: at 85% of
  the e4m3 roof the band would be ~0.035 ms/row at M=160.
- **Revised forecast:**
  - Existing kernels with a captured pass (glue 3): +4.7..+5.4% (B=128-144). Glue 5: +2.3..+3.1%.
  - A new TP-shape GEMM at ~85% of roof (band 0.035) + captured pass: **payoff if it works +8%** (B=96, glue 3).
    The ideal kernel gives +11%.
  - Central +3%. Odds of >= +5%: ~25%.
- **Revised roadmap:**
  1. Kernel feasibility first (~10 GPU-min): one TP-shape kernel prototype (stream-K / smaller N tiles, from bs_gemm),
     gate_up and down at M=128-160 in the chain. Gate: <= 0.04 ms/row.
  2. Then the captured mixed pass, then the ABBA, as before.
  - Total ~80 GPU-min unchanged. Stop after step 1 if its gate fails.

## Update after the cause-directed variant (bank/T51-003, job 438, 1.7 GPU-min): screen negative
- 4 CTAs/SM and split-K down leave the band at 65-99 us/row. Occupancy is not the limiter; the cause is unidentified.
- Config-level fixes of the existing kernel are exhausted. Passing the gate needs a new kernel design for M=128-192 on TP
  shapes. Its feasibility is unproven, and earlier teams' custom decode GEMMs often fell short (KB83, KB96, KB101).
- **Forecast now:** payoff if it works unchanged (+8%; it rests on a kernel at ~85% of the e4m3 roof). Central +2%.
  Odds of >= +5%: ~15%.
- **Recommendation:** fund only a bounded kernel-design step, ~25 GPU-min: stream-K or a balanced-grid gate_up/down
  prototype at M=128-160, chain gate <= 0.04 ms/row. Otherwise close T51 with the write-up. The captured-pass work is
  not worth starting until the kernel gate passes.
