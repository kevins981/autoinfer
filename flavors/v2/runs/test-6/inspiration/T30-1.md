# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Per-item overhead

**The principle.** The cost of a piece of work often has two parts: one that grows with its size, and a fixed part paid every time regardless of size (setting up, starting, switching, handing over). When items are small, the fixed part dominates. The fixed part belongs to the act of starting, not to the work itself, so several items can share one.

**The waste.** Fixed costs paid more often than necessary.

**General directions.**
- **Group items:** pay the fixed part once for many.
- **Join steps:** let an item pass through several steps without stopping and restarting between them.
- **Stay set up:** keep the preparation between items instead of tearing it down and rebuilding it.
- **Shrink the fixed part:** if it can't be shared, make it cheaper.

**Illustrations** (examples only; the best use of this principle may look like none of them). A bus carries fifty people with one driver. Laundry is done by the load. Goods cross the ocean in containers, not parcel by parcel.

(card: `10-per-item-overhead.md`)

### Mismatch with the machine

**The principle.** A machine is not equally good at everything. It has operations and patterns it performs very fast, and others it performs slowly; the difference can be large. The same result can usually be reached through work of different shapes. Speed depends on the fit between the shape of the work and the strengths of the machine, as much as on the amount of work.

**The waste.** Work in a shape the machine does slowly, when an equivalent shape would use what it does fast.

**General directions.**
- **Learn the machine:** what is it fast at, and which of its capabilities are rarely used?
- **Reshape the work:** sizes, order, arrangement, kind of operation, so that it fits.
- **Move work to the part that suits it:** different parts of a machine have different strengths.
- **Ask what is unused:** a capability nobody uses may fit a problem nobody matched it to.

**Illustrations** (examples only; the best use of this principle may look like none of them). Boxes sized to the truck bed fill it with no gaps. A car is efficient only in the right gear. Multiplying by two is a shift for a binary machine.

(card: `17-mismatch-with-the-machine.md`)

### Timing

**The principle.** The same work costs different amounts depending on when it is done. At some moments it delays everything that waits on it; at others, capacity is free and nothing is waiting. Every piece of work has a window: it cannot start before its inputs are known, and it must finish before its output is needed. Anywhere inside the window is correct.

**The waste.** Work done at an expensive moment in its window, when a cheaper moment exists.

**General directions.**
- **Do it early:** as soon as the inputs are known, or in a quiet period.
- **Do it late:** after the urgent work, or when more is known; sometimes it turns out not to be needed.
- **Take it off the path others wait on:** the work still happens, but nothing waits for it.
- **Gather it:** hold work until a moment when it is cheap to do together.

**Illustrations** (examples only; the best use of this principle may look like none of them). A chef does the chopping before service starts. A bank settles the day's payments overnight. A shop restocks shelves after closing.

(card: `07-timing.md`)

### Coordination

**The principle.** When parts work at the same time on related things, they must agree: wait for each other, take turns on what they share, exchange what they know. This work produces no output. It exists only because the work was divided. It grows with how much is shared and how often agreement is required, not with the amount of useful work.

**The waste.** Time spent agreeing, and waiting to agree.

**General directions.**
- **Share less:** divide the work so the parts need little from each other.
- **Agree less often:** exchange at longer intervals, or only when something changed.
- **Agree on less:** only what must be common; the rest can stay local.
- **Proceed and reconcile:** let parts continue without waiting, and settle differences afterwards.

**Illustrations** (examples only; the best use of this principle may look like none of them). A team's meetings grow faster than the team. A roundabout lets cars flow without waiting for a signal. Each cook in a kitchen has their own station.

(card: `12-coordination.md`)

### Imbalance

**The principle.** A system has several resources: time, memory, capacity to move things, different kinds of processing. They are rarely all scarce at once. Usually one limits the system and the others have room to spare. Most work can be done in more than one way, each using a different mix of resources. Gains come only at the limiting resource; spending the others costs nothing until they run out.

**The waste.** A plentiful resource left unused while a scarce one limits the system.

**General directions.**
- **Find the limit:** which resource is the system actually waiting for?
- **Spend the plentiful to save the scarce:** choose the way of working that leans on what is spare.
- **Trade in either direction:** more memory for less work, or more work for less memory or movement.
- **Check again:** after a change the limit may have moved to another resource.

**Illustrations** (examples only; the best use of this principle may look like none of them). A table of answers spends space to save time; compression spends time to save space. A slow cooker spends hours to save attention. A factory with idle machines and too few workers reorganizes around the workers.

(card: `14-imbalance.md`)

## This machine: hardware

### Memory that lives on both sides

**What it is.** Unified (managed) memory is one address range valid on the host and on the GPU. Pages move to whichever side touches them, and both sides can hold pages at the same time. A program can give hints: where a range should preferably live, that it is mostly read, or that it should be moved now ahead of use. A range may be larger than the GPU's free memory; pages are evicted to the host as needed. Ordinary pageable host memory cannot be read by the GPU directly on this system.

**What it makes possible.** Data need not have one fixed home, and the total can exceed what the GPU holds, at the price of page moves when the wrong side touches a page.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Unified Memory.

(card: `10-memory-that-lives-on-both-sides.md`)

### Graphics hardware a compute program can reach

**What it is.** The chip carries hardware built for graphics that compute code can also use. Texture units fetch from a 1-, 2- or 3-dimensional array and blend the neighbouring entries in hardware in a single fetch (the blend weights have limited precision), with built-in handling of out-of-range coordinates; arrays can be up to 131,072 wide in one dimension. The ray-tracing units search a hierarchy of bounding boxes in hardware; they are reached through a separate library.

**What it makes possible.** A table lookup with interpolation, or a search over spatial data, can be done by dedicated hardware that is otherwise idle in a compute program.

**How this was checked.** Texture limits queried from the device. The ray-tracing path was not checked on this machine.

**Where to read more.** CUDA Programming Guide: texture and surface memory; the OptiX documentation.

(card: `18-graphics-hardware-a-compute-program-can-reach.md`)

### What this chip does not have

**What it is.** Several features of newer NVIDIA chips are absent on this one: thread-block clusters and scratch memory shared across SMs; the bulk copy unit (TMA) that loads whole tiles with one instruction; moving registers between warps while a kernel runs; add, subtract and multiply directly on bfloat16 values (fused multiply-add on bfloat16 does exist); the block-scaled and 4-bit float formats. Scratch memory per SM is 100 KB, less than on the older data-center chip of the same family (164 KB) and the newer one (228 KB).

**What it makes possible.** Code written for newer chips often assumes these features. Here the same job has to be done another way, or the code falls back to a slower path without saying so. Knowing what is missing tells you which published designs carry over unchanged and which need rethinking.

**How this was checked.** The compiler rejects cluster launch for this chip; the assembler rejects the bulk copy, register reallocation and bfloat16 add; the device reports no cluster launch and no tensor-map access.

**Where to read more.** CUDA Programming Guide: Compute Capabilities; PTX ISA reference (the target notes under each instruction).

(card: `03-what-this-chip-does-not-have.md`)

### No direct path between the two GPUs

**What it is.** On this machine one GPU cannot read or write the other's memory (peer-to-peer access is reported as not supported), and there is no dedicated GPU-to-GPU link. Data going from one GPU to the other travels up one link into host memory and down the other link. Libraries that depend on direct access between GPUs do not apply here.

**What it makes possible.** Every exchange between the GPUs has two hops and passes through memory the host processors can also see. The host is on the path whether it takes part or not.

**How this was checked.** `nvidia-smi topo -p2p r` reports peer-to-peer as not supported.

**Where to read more.** CUDA Programming Guide: Programming Systems with Multiple GPUs.

(card: `21-no-direct-path-between-the-two-gpus.md`)

### Main memory and how fast it can be read

**What it is.** Each GPU has 24 GB of GDDR6X memory on a 384-bit bus clocked at 10,501 MHz. At 21 Gbit/s per pin that is a theoretical peak of 1,008 GB/s. There is no error correction. The memory is not shared between the two GPUs.

**What it makes possible.** The peak rate puts a floor under any step that must read a given number of bytes: bytes divided by rate. Comparing that floor with a step's measured time shows whether the step is limited by reading memory or by something else.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes). The peak rate is arithmetic from the bus width and data rate, not a measurement.

**Where to read more.** Ada Tuning Guide; the Nsight Compute memory metrics.

(card: `05-main-memory-and-how-fast-it-can-be-read.md`)

## This machine: software

### Compiling while the program runs

**What it is.** GPU code does not have to be compiled before the program starts. A program can generate source, compile it in memory (NVRTC), link it with other compiled pieces while still optimizing across them (nvJitLink), and load the result, all while running. The Python kernel languages here work this way already.

**What it makes possible.** At run time the program knows things that were unknown beforehand: sizes, shapes, constants, which case actually occurs. Code compiled then can have them built in.

**How this was checked.** The libraries are installed (NVRTC 13.0, nvJitLink 13.4); not exercised here.

**Where to read more.** NVRTC and nvJitLink documentation; `cuda.core` documentation.

(card: `02-compiling-while-the-program-runs.md`)

### Sharing without copying

**What it is.** Several mechanisms let two parties use the same bytes. Host processes can share memory by name (63 GB available in the memory-backed file system). GPU memory can be shared between processes. Libraries in one process can hand each other GPU arrays without a copy through a standard exchange format (DLPack) or a common array interface. Message passing between processes is available with zero-copy for large messages.

**What it makes possible.** A boundary between processes or between libraries does not have to cost a copy.

**How this was checked.** The mechanisms are present in the installed software; not exercised here.

**Where to read more.** DLPack; PyTorch `torch.multiprocessing`; CUDA Programming Guide: Interprocess Communication; ZeroMQ guide.

(card: `08-sharing-without-copying.md`)

### Parallel building blocks

**What it is.** A library of general parallel algorithms for the GPU is installed, in C++ and with a Python interface: sort, scan (running totals), reduce, select the items that meet a condition, partition, remove duplicates, histogram, run-length encode, search, merge.

**What it makes possible.** Problems that look inherently sequential, such as compacting a list or grouping equal items, have well-known parallel forms that are already written.

**How this was checked.** The package is installed (CCCL 13.3); not exercised here.

**Where to read more.** CCCL documentation (Thrust, CUB, `cuda.cccl`).

(card: `06-parallel-building-blocks.md`)

### How Python runs

**What it is.** The Python here is 3.12. One thread at a time executes Python code within an interpreter; the others wait for a lock. Native code called from Python can release the lock while it works, and most heavy library calls do. Separate processes each have their own lock, and so can separate interpreters within one process (in this version they can only be created from native code). Starting a thread is cheap and it shares all memory; a process is isolated and shares only what is arranged.

**What it makes possible.** Whether two pieces of host work truly overlap depends on where the lock is held, not on how many threads exist.

**How this was checked.** Version read from the environment. Whether a given library call releases the lock has to be checked case by case.

**Where to read more.** Python documentation: the global interpreter lock, `threading`, `multiprocessing`.

(card: `09-how-python-runs.md`)

### The communication library, beyond one operation

**What it is.** The library that moves data between GPUs (NCCL 2.30) offers more than the sum-across-GPUs operation: broadcast, reduce to one GPU, gather from all, reduce-then-scatter, and plain send and receive between two GPUs. Several operations can be grouped and issued together. Buffers can be registered ahead of time. It has a Python interface. Its newest feature, communication started from inside a kernel, needs direct GPU-to-GPU access and so does not apply on this machine.

**What it makes possible.** The exchange pattern between the GPUs is a choice from a larger set than the one in use, and the library is not the only way to move data.

**How this was checked.** The package and its Python interface are installed. Which transport it selects on this machine was not checked here.

**Where to read more.** NCCL user guide and release notes.

(card: `07-the-communication-library-beyond-one-operation.md`)
