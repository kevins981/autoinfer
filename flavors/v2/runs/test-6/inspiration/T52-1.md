# Inspiration cards

These cards are offered for inspiration only. Nobody chose them for your team, and they are not a
direction or an assignment.

- **Look at the system yourself first:** read the task, profile, find where the time goes. Then
  come back to the cards. Using none of them is fine.
- **The principle cards are general.** They say nothing about this system; applying them is your
  work.
- **The hardware and software cards are high-level pointers, not a reference.** They may be
  incomplete, out of date or wrong for your case, and each says how it was checked. Do your own
  research and verify any detail before you rely on it.

## General principles

### Generality

**The principle.** Work that can handle many cases has to find out which case it is in, and has to be built so that every case stays possible. The more that is known in advance about the inputs, the less there is to decide and the less work remains. Every fact that is fixed in this situation (a size, a type, a range, a condition that always holds) is a decision that could be made once, ahead of time, instead of every time.

**The waste.** Checks, indirection and cautious choices that exist for cases which never occur here.

**General directions.**
- **Fix what is known:** build a version for the case that actually occurs.
- **Remove decisions with one answer:** a check that always comes out the same isn't a check.
- **Use a narrower method:** one that only works under the conditions that hold here can be cheaper.
- **Keep the general version as a fallback:** the special version only needs to cover what it was built for.

**Illustrations** (examples only; the best use of this principle may look like none of them). A key fits one lock; a locksmith's toolkit opens any, slowly. A compiler replaces a calculation on constants with its result. A production line built for one product outruns a general workshop.

(card: `03-generality.md`)

### Unused results

**The principle.** Work has value only through what uses its output. Follow any output forward: if nothing reads it, or only part of it is read, the unread part bought nothing. This happens because the producer usually doesn't know what the consumer will need, so it produces everything to be safe.

**The waste.** Work whose output nobody uses, and the unused part of outputs that are only partly used.

**General directions.**
- **Produce on demand:** wait until something asks for the output.
- **Produce only the part asked for:** let the request say how much is needed.
- **Tell the producer:** pass the consumer's needs back to where the work is done.
- **Stop early:** once the answer is determined, the rest of the work adds nothing.

**Illustrations** (examples only; the best use of this principle may look like none of them). A restaurant cooks to order instead of cooking the whole menu. A search stops at the first match when one is enough. A map loads only the area on the screen.

(card: `02-unused-results.md`)

### Boundaries

**The principle.** Systems are divided into parts so that each can be built and understood on its own. Every boundary has two costs:
- **Crossing:** things are converted, copied, checked and handed over.
- **Blindness:** each part decides with only what it can see. It can't use what its neighbours know, so it must assume the worst.

**The waste.** The cost of crossing, plus the better decisions missed because knowledge stops at the boundary.

**General directions.**
- **Pass knowledge across:** tell the other side what you know, so it needn't assume or rediscover it.
- **Merge parts:** that work on the same thing.
- **Go around a layer:** when the service it provides isn't needed on this path.
- **Move the boundary:** to where fewer things cross it.

**Illustrations** (examples only; the best use of this principle may look like none of them). Two people who share a language need no interpreter. A form that passes through five departments waits at each desk. A compiler that sees across a function call can simplify both sides.

(card: `11-boundaries.md`)

### Representation

**The principle.** The same information can be written in many forms. Forms differ in size, and in which operations are cheap on them. The cost of storing, moving and processing follows the form, not the information. A form is usually chosen once, for convenience, and everything afterwards pays for it.

**The waste.** Extra size and extra steps caused by the form, not by the information.

**General directions.**
- **A smaller form:** no larger than the information it holds.
- **A form that makes the frequent operation cheap:** even if rare operations get dearer.
- **Arrange for use:** put next to each other what is used together.
- **Convert once:** at the edge, not repeatedly inside.
- **Several forms:** the same information kept in different forms for different uses.

**Illustrations** (examples only; the best use of this principle may look like none of them). Arithmetic is easy in Arabic numerals and hard in Roman ones. A phone book is sorted by name because that is how it is searched. A map and a list of turns hold the same route for different uses.

(card: `13-representation.md`)

### Distance

**The principle.** Work needs its inputs at the place where it happens. Moving things takes time in proportion to how much is moved and how far, and the paths have limited capacity. Time spent moving is not time spent working. How much movement there is depends on where things are kept and where the work is done, and both are choices.

**The waste.** Movement that a different placement would avoid.

**General directions.**
- **Bring the work to the data:** instead of the data to the work.
- **Keep together what is used together:** so one trip serves many needs.
- **Move less:** only the part that is needed, or a smaller form of it.
- **Move once:** not the same thing back and forth.
- **Keep the most used nearest:** the nearest places are few; give them to what is needed most often.

**Illustrations** (examples only; the best use of this principle may look like none of them). A workshop keeps its most used tools within arm's reach. A retailer puts warehouses near its customers. A question is sent to the database instead of fetching the whole table to answer it.

(card: `09-distance.md`)

## This machine: hardware

### Fetching without waiting, inside a kernel

**What it is.** A kernel can start a copy from main memory into its scratch memory and continue working while the copy is in flight. The data does not pass through registers. Barrier objects tell the kernel when a batch of copies has landed, and several batches can be in flight at once (a pipeline).

**What it makes possible.** Fetching the next piece of data can overlap with computing on the current piece, inside a single kernel, instead of the two alternating.

**How this was checked.** Each instruction was assembled for this chip (`ptxas -arch=sm_89`); not run. The bulk form of this copy is not available on this chip.

**Where to read more.** CUDA Programming Guide: Asynchronous Data Copies; Pipelines; Asynchronous Barriers.

(card: `08-fetching-without-waiting-inside-a-kernel.md`)

### The paths between the parts

**What it is.** Each GPU connects to the host by its own PCIe link (generation 4, 16 lanes) on its own port. Both links attach to the first processor socket. A link carries about 32 GB/s in each direction at most. A GPU reads its own memory about 30 times faster than that.

**What it makes possible.** Anything that crosses a link is far more expensive per byte than anything that stays on a GPU. How many bytes cross, and how often, is set by how the work is divided.

**How this was checked.** Topology read from `nvidia-smi` and `lspci`. The link rate is the standard's figure, not a measurement.

**Where to read more.** PCI Express specification summaries; `nvidia-smi topo -m`.

(card: `20-the-paths-between-the-parts.md`)

### What this chip does not have

**What it is.** Several features of newer NVIDIA chips are absent on this one: thread-block clusters and scratch memory shared across SMs; the bulk copy unit (TMA) that loads whole tiles with one instruction; moving registers between warps while a kernel runs; add, subtract and multiply directly on bfloat16 values (fused multiply-add on bfloat16 does exist); the block-scaled and 4-bit float formats. Scratch memory per SM is 100 KB, less than on the older data-center chip of the same family (164 KB) and the newer one (228 KB).

**What it makes possible.** Code written for newer chips often assumes these features. Here the same job has to be done another way, or the code falls back to a slower path without saying so. Knowing what is missing tells you which published designs carry over unchanged and which need rethinking.

**How this was checked.** The compiler rejects cluster launch for this chip; the assembler rejects the bulk copy, register reallocation and bfloat16 add; the device reports no cluster launch and no tensor-map access.

**Where to read more.** CUDA Programming Guide: Compute Capabilities; PTX ISA reference (the target notes under each instruction).

(card: `03-what-this-chip-does-not-have.md`)

### Several processes on one GPU

**What it is.** By default, processes that use the same GPU take turns: the GPU switches between them in time slices, and only one runs at any instant. The multi-process service (MPS) funnels several processes into one shared context so their kernels can run at the same time, and can cap each process's share of the GPU. An ordinary user can start the service for their own processes; its control program is installed. It is not running now, and other people use this machine.

**What it makes possible.** Whether work split across processes overlaps or alternates on the GPU is a choice, not a fixed property.

**How this was checked.** The device reports the default sharing mode and that MPS is off. Starting MPS was not tried.

**Where to read more.** NVIDIA Multi-Process Service documentation.

(card: `14-several-processes-on-one-gpu.md`)

### More than one kernel at a time

**What it is.** A GPU can have up to 128 kernels resident at once. Kernels issued on different streams of one process may run at the same time when the first leaves SMs, registers or scratch memory free; otherwise they run one after another. Streams can be given priorities. The two GPUs are fully independent of each other.

**What it makes possible.** A small kernel does not have to wait behind a large one, and a kernel that cannot use the whole chip need not leave the rest idle.

**How this was checked.** Queried from the device on this machine (CUDA driver API device attributes).

**Where to read more.** CUDA Programming Guide: Asynchronous Execution.

(card: `12-more-than-one-kernel-at-a-time.md`)

## This machine: software

### Several levels of language for GPU code

**What it is.** GPU code can be written at different levels, and several are installed here. At thread level: CUDA C++ (compiler 13.0) and Numba (Python compiled to the same thing). At block level: Triton, where one program describes a whole thread block and the compiler arranges the threads. At tile level: NVIDIA's CuTe DSL (the building blocks of its matrix-kernel library, usable from Python) and cuTile (kernels written as operations on whole tiles).

**What it makes possible.** The level sets what the author controls and what the compiler decides. The same kernel can be cheap to write at one level and only reach full speed at another, and pieces written at different levels can live in one program.

**How this was checked.** All import in this environment. cuTile's compiler was not run on this chip.

**Where to read more.** CUDA Programming Guide: Writing SIMT Kernels, Writing Tile Kernels; the Triton, Numba, CuTe DSL and cuTile documentation.

(card: `01-several-levels-of-language-for-gpu-code.md`)

### The framework underneath

**What it is.** The framework keeps its own pool of GPU memory and hands out pieces without asking the driver each time; the pool's behaviour can be tuned and inspected. New operations can be written in C++ or CUDA and loaded as extensions, built ahead of time or when the program starts. The framework exposes streams, events, pinned host memory and non-blocking copies. Each operation passes through a dispatch layer on the host before any GPU work is issued.

**What it makes possible.** The framework's defaults are one arrangement among several it supports, and anything it lacks can be added beside it.

**How this was checked.** From the installed framework (torch 2.14); not exercised here.

**Where to read more.** PyTorch documentation: CUDA semantics, memory management, C++ extensions.

(card: `10-the-framework-underneath.md`)

### The communication library, beyond one operation

**What it is.** The library that moves data between GPUs (NCCL 2.30) offers more than the sum-across-GPUs operation: broadcast, reduce to one GPU, gather from all, reduce-then-scatter, and plain send and receive between two GPUs. Several operations can be grouped and issued together. Buffers can be registered ahead of time. It has a Python interface. Its newest feature, communication started from inside a kernel, needs direct GPU-to-GPU access and so does not apply on this machine.

**What it makes possible.** The exchange pattern between the GPUs is a choice from a larger set than the one in use, and the library is not the only way to move data.

**How this was checked.** The package and its Python interface are installed. Which transport it selects on this machine was not checked here.

**Where to read more.** NCCL user guide and release notes.

(card: `07-the-communication-library-beyond-one-operation.md`)

### Parallel building blocks

**What it is.** A library of general parallel algorithms for the GPU is installed, in C++ and with a Python interface: sort, scan (running totals), reduce, select the items that meet a condition, partition, remove duplicates, histogram, run-length encode, search, merge.

**What it makes possible.** Problems that look inherently sequential, such as compacting a list or grouping equal items, have well-known parallel forms that are already written.

**How this was checked.** The package is installed (CCCL 13.3); not exercised here.

**Where to read more.** CCCL documentation (Thrust, CUB, `cuda.cccl`).

(card: `06-parallel-building-blocks.md`)

### Compiling while the program runs

**What it is.** GPU code does not have to be compiled before the program starts. A program can generate source, compile it in memory (NVRTC), link it with other compiled pieces while still optimizing across them (nvJitLink), and load the result, all while running. The Python kernel languages here work this way already.

**What it makes possible.** At run time the program knows things that were unknown beforehand: sizes, shapes, constants, which case actually occurs. Code compiled then can have them built in.

**How this was checked.** The libraries are installed (NVRTC 13.0, nvJitLink 13.4); not exercised here.

**Where to read more.** NVRTC and nvJitLink documentation; `cuda.core` documentation.

(card: `02-compiling-while-the-program-runs.md`)
