- **TokenWeave** (deck card 03; arXiv 2505.11329) and **NanoFlow** (OSDI'25): hide TP collectives by running independent token groups' compute under them. The condition they need is copies that coexist with compute without contention.
  - Here (measured, T30-005 trace, n=734 captured replay): copy rate 20.7 GB/s with compute vs 21.3 without; GEMMs not slowed; copies active in 95% of the gap time.
  - The condition holds in big mixed steps, unlike decode (KB59/62).
- **Graph-captured (persistent) execution** (deck card 02, MPK, in the weak form of CUDA graphs): the wave schedule's in-server blocker is host enqueue, not the GPU (eager k=2 waves 189-212 ms wall vs 123.6 ms host-free, T30-004/005).
- **TokenWeave's byte-cutting reduce-scatter + all-gather** (adapted: all-gather the next W8A8 GEMM's e4m3 input), as an optional third part.

## Concrete capture design for A (from reading the code)
- In the fla chunked GDN, the host work is `prepare_chunk_indices` (`.tolist()` on cu_seqlens) plus Triton grids that depend on N sequences and NT chunks of 64 (chunk_delta_h.py:303-321).
- `chunk_gated_delta_rule` accepts precomputed `chunk_indices`, so the metadata can be built once per step, not per layer/wave.
- Plan: capture per bucket (N prefill sequences 1-4, NT padded up to a grid). Padding is a dummy trailing sequence whose state slot is scratch, so real states are untouched. Mixed steps carry 1-3 prefill sequences and NT <= ~24: a few dozen buckets per layer type.
- The T30-005 replay already showed the eager forward of a step is capturable.

## Roadmap with kill gates
**Stage 0, seed (<= 15 of my 19.8 GPU-min), 1 worker:**
- **A-feasibility:** one GDN layer at real mixed shapes (N = 1/2/3, NT = 4..24), captured per bucket with dummy-sequence padding vs eager.
  - Gate: output and final/intermediate states **bitwise** equal for the real sequences.
  - Gate: host time per captured call <= 0.15 ms (eager ~1.24 ms), including the per-step metadata build.
  - Gate: GPU time incl. padding <= +10%.
- **B-feasibility (optional, cheap):** the two-phase path on the champion's device-flag DMA AR (dma_staged_ar.cu) at R = 256/734/1024.
  - Gate: >= 15% faster than the current AR at R >= 512. If it fails, B is dropped and the payoff falls to A+C (+4.3-5.5%).

**Stage 1, start grant (80 GPU-min):**
- Integrate the captured GDN core into champion mixed steps, then T30's k-wave scheduler (workspace t30-wave, T30_WAVE_K) on top.
- Gate: in-server big-step GPU span within ~5 ms of the replay (e.g. <= 121 ms at n~734).
- Gate: same-job ABBA (abba.sh) all-B > all-A, >= +2%.
- Exact by construction (same kernels, a different launch method and ordering); bitwise check of states at startup.

**Stage 2, extension (~60-80 GPU-min), only if stage 1 passes:**
- C: W8A8 tiles / stream-K for M 128-400.
- B: if its stage-0 gate passed and the ruling allows.
- Then GSM8K A/B if FP8 code changes, 128K check, official eval.

GPU time requested: start grant 80 after stage 0 passes; ~170 total.

## Validity notes
- A: exact (launch method and ordering only; padding confined to a scratch state slot).
- C: exact up to fp32 reordering under the existing FP8-activation A/B rule (new GEMM kernel = new A/B).
- B: needs a ruling. It sends the e4m3 bytes and fp32 group scales the W8A8 GEMM consumes, quantized once by the token owner with the same per-token-group-128 math. The residual stream becomes token-sharded between ARs. in_proj_ba's bf16 input needs owner-side computation (duplicate the 1 MB/layer ba weight).
